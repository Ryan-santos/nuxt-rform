`RForm` is not a field: it is what provides the root of the injection. Every
field inside it reads the form model through `inject`, and that is what makes
`name` mean "this key of the model" rather than "this isolated input".

It is also what provides the **form root** — the `form` every `rule` receives.
Neither `RArray` nor `RObject` overrides it, so a field nested three levels deep
still sees the whole form.

## The three useRForm modes

What changes between them is **where** the UI, the types and the validation come
from.

### 1 · full schema

`useRForm(schema)` returns `data`, `rules` and `schema`. `RForm` takes the
schema and builds the form on its own — there is not a single field tag written
by hand.

::demo{src="Form/modo-schema" title="the schema is the data" :form="false"}
::

::callout{type="info"}
In `schema` mode every field already carries its own `rule`, so passing `:rules`
here would validate twice — same preset, same message, one extra parse. `:rules`
exists for **zod mode**, where the UI is written by hand and the aggregate is the
only source.
::

### 2 · zod only

Given an object of nothing but `ZodType`, `useRForm` returns `data` and `rules`
— and no `schema`. The UI is yours; the aggregated `rules` validates the whole
object on submit, and `RForm`’s `:rules` is what consumes it: every zod issue
lands on the field that owns it, following its `path`.

::demo{src="Form/modo-zod" title="types and validation from zod, UI by hand" :form="false"}
::

### 3 · TS only

`useRForm<T>()` receives nothing at runtime: it only types `data`. No `rules`
and no `schema` — validation is whatever presets each field declares.

::demo{src="Form/modo-ts" title="zero runtime cost" :form="false"}
::

::callout{type="warn"}
`safeParseAsync`, not `safeParse`: a `rule` referenced by preset name becomes
`z.any().superRefine(async …)` in the aggregated object, and a synchronous parse
would throw. A zod-only schema stays synchronous.
::

## Errors from the outside

Not every error is born in the browser. "This ID is already registered" only
exists after the server answered, and for that case `RForm` has two doors — both
keyed by the field’s `name`.

The first is the **return of `onSubmit`**: returning an errors object lands each
message on the field that owns it.

```ts
const send = async (data: Signup) => {
    const { errors } = await $fetch("/api/signup", { method: "POST", body: data });

    // Nothing returned = it worked. An object = per-field errors.
    return errors;
};
```

The second is `setErrors`, through the template `ref` — for an error that did not
come from a submit.

```vue
<template>
    <RForm ref="form" v-model="data">
        <RText name="name" />
    </RForm>
</template>

<script setup lang="ts">
    const form = useTemplateRef("form");

    form.value?.setErrors({ name: "Name already taken" });
</script>
```

::demo{src="Form/erros-api" title="the server writes into the field" :form="false"}
::

The key is the field’s `name`, and it may arrive **nested** or **dotted** — both
mean the same thing, mixed forms included. An `RArray` index is just another
segment:

```ts
{ address: { zip: "Invalid ZIP" } }   // nested
{ "address.zip": "Invalid ZIP" }      // dotted
{ "partners.0.id": "Invalid ID" }     // inside an RArray
{ name: ["Already taken"] }           // string[] → the first item
```

A message coming in this way is **final text**, not a key: it came from the
server, which already knows what language to answer in, and the module writes it
into the field without going through the translator. The one that takes a key is a
field’s `:error` — see [Translation](/en/concepts/traducao).

::callout
This is the **only** channel in `schema` mode and in
[`RDynamic`](/en/form/dynamic): there is no hand-written field tag there to take
an `:error`.
::

A root issue — a `superRefine` over the whole object, with no `path` — becomes the
`""` key. No field has that `name`, so it shows up in the return of `submit` and
renders nowhere.

The template `ref` exposes `model`, `validate`, `submit`, `setErrors` and
`errors`; the default slot exposes the last four minus `errors`. `validate()`
returns `true`/`false` and never rejects; `submit()` returns `undefined` when
everything passed, or the map of errors.

## Focus on the first error

Whenever an error shows up — on validation or on a `setErrors` coming from the
API — the first field with an error takes focus and the page scrolls to it.
"First" means **document** order, not registration order: the DOM is what
answers, so it works the same for a hand-written form and for one `RDynamic`
built.

To turn it off:

```vue
<RForm :focus-error="false" v-model="data">
```
