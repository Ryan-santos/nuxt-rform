A form is rarely a flat list. The postcode only matters when delivery is to an
address; the request body only exists when the type isn't `none`.

In template mode this is already solved: you write Vue's own `v-if`. In `schema`
mode **there is no markup to write it in** — a `<RDynamic :schema>` coming from a
server route has to say it in the data. That's what `visibleWhen` and
`disabledWhen` are for, and it's why both are keys of the **schema**, not field
props.

::demo{src="Form/condicional" title="the sibling decides" :form="false"}
::

## Where they apply

`RDynamic` is what reads them: it decides whether to mount the field, and it fills
in that field's `disabled`.

::callout{type="warn"}
**On a hand-written tag they don't exist.** `<RText :visible-when="…">` matches no
prop and lands as a loose attribute. In markup the answer is `v-if`:

```vue
<RTextarea
    v-if="data.tipo !== 'none'"
    name="body"
/>
```
::

A field that leaves the screen through `v-if` also leaves validation — it unmounts
and takes its own `rule` with it.

## The shape of a condition

```ts
{ field: "entrega", op: "===", value: "casa" }
```

`field` is always a **dotted path from the root of the form** — never relative to
the field declaring the condition. It walks into objects and array indexes:

```ts
{ field: "endereco.uf", op: "===", value: "SP" }
{ field: "socios.0.cpf", op: "is_not_empty" }
```

::callout{type="warn"}
**`op` is required and has no default.** `{ field: "idade", value: 18 }` doesn't
compile. The difference between `==` and `===` stays written in the schema, which
is where it has to be when you don't control whether the field yields `"18"` or
`18`.
::

## The operators

| `op` | the field | `value` | matches when |
|---|---|---|---|
| `==` `!=` `===` `!==` | anything | anything | the same JS operator |
| `>` `>=` `<` `<=` | number, string, date | same | the JS comparison |
| `in` `not_in` | scalar | **array** | the field is in the list |
| `contains` `not_contains` | string or array | scalar | the field contains the value |
| `starts_with` `ends_with` | string | string | starts / ends with |
| `matches` | string | regex source | `new RegExp(value, flags).test(field)` |
| `is_empty` `is_not_empty` | anything | — | empty: `undefined`, `null`, `""`, `[]`, `{}` |

`in` and `contains` are inverses, and both exist: the first asks whether the field
is in a fixed list from the schema, the second whether the field — a multiple
`RSelect`, a string — contains an item.

`is_empty` does **not** match `false` or `0`: the field answered.

Only `matches` takes `flags`, and it needs them, because `(?i)` doesn't exist in
JavaScript:

```ts
{ field: "cupom", op: "matches", value: "^promo", flags: "i" }
```

## Composing

An array is **AND**, `{ or }` is **OR**, `{ not }` inverts — and all three nest.

```ts
// shows up when delivery is to an address AND the postcode is filled in
visibleWhen: [
    { field: "entrega", op: "===", value: "casa" },
    { field: "cep", op: "is_not_empty" }
]

// shows up for companies OR when revenue is over a thousand
visibleWhen: {
    or: [
        { field: "tipo", op: "===", value: "pj" },
        { field: "faturamento", op: ">", value: 1000 }
    ]
}

visibleWhen: { not: { field: "tipo", op: "in", value: ["pf", "mei"] } }
```

When the declarative form doesn't reach, a function gets the same pair a `rule`
gets — `value` is the field's own value, `form` is the whole form:

```ts
visibleWhen: ({ form }) => form.itens.length > 3
```

::callout{type="info"}
The types cover **four levels** of nesting, which is `[{ or: [{ not: […] }] }]`.
The runtime evaluator has no limit; only autocompletion stops there.
::

## What happens to the value, and to validation

**A hidden field drops out of validation and keeps its value in the model.** Both
halves matter:

- out of validation — a `rule: "required"` on a field that isn't on screen can't
  fail the submit, and that holds for all three error sources (the field's `rule`,
  the aggregated `:rules`, and a pending upload);
- keeps its value — showing the field again brings back what was typed, and what
  you send to the server is still the whole model. If a hidden field shouldn't go
  along, delete the key in `onSubmit`.

Hiding an `object` drops its children's errors too.

::callout{type="warn"}
**A disabled field is still validated.** It changes interaction and appearance;
the value is in the model all the same, and the HTML isn't the authority on that.
To take a field out of validation, use `visibleWhen`.
::

## `disabled` and `disabledWhen`

`disabled` is a prop on every field, and it works in both modes:

```vue
<RText name="entrega" disabled />
```

`disabledWhen` is the schema's version, and the explicit prop **beats** the
condition, both ways — `disabled: false` keeps the field live even when the
condition says otherwise:

```ts
{
    entrega: { type: "text", label: "Address" },
    complemento: {
        type: "text",
        disabledWhen: { field: "entrega", op: "is_empty" }
    }
}
```

A disabled field gets `pointer-events-none opacity-60` on its container and the
native `disabled` on the control, which is what takes it out of the Tab order. To
restyle it, the key is `ui.disabled`.

::callout
`disabled` on an `object` or an `array` does **not** cascade to its children: CSS
blocks the mouse, but nothing leaves the Tab order. To disable a child, put
`disabledWhen` on the child.
::

## snake_case in the schema

In schema mode the object usually comes from an API, and there `visible_when` is
accepted just as much as `visibleWhen`. The rule is general and covers every
compound prop — `disabled_when`, `model_full`, `on_search`:

```ts
{
    type: "textarea",
    rule: "required",
    visible_when: { field: "body_type", op: "in", value: ["json", "form"] }
}
```

The translation is anchored on the props the component actually declares, so a key
it doesn't know passes through untouched and nothing gets renamed by accident.
Write both on the same field and the camelCase one wins.

## A schema with no `RForm` around it

The condition resolves against the form's model, so a `<RDynamic :schema>` used
outside an `RForm` has nothing to resolve it against. In that case it is
**ignored** — the field shows up and stays enabled — and a warning naming the prop
goes to the console. Hiding the field silently would be worse.
