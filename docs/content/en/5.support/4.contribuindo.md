## Running

The package manager is **pnpm**, and the repo is a workspace: one `pnpm install`
at the root covers the module, the site and the four playgrounds.

```bash
pnpm install
pnpm dev:prepare   # populates each app's .nuxt and #rform
```

::callout{type="warn"}
Running `pnpm install` **inside** one of the subprojects installs nothing: it
resolves to the root and answers "Already up to date", in 30 ms and with exit 0.
It fails silently.
::

## The apps

| command                | what                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `pnpm run docs`        | this site                                                   |
| `pnpm play`            | the `i18n` playground — language switching, user packs      |
| `pnpm play:basic`      | a normal app with `@nuxtjs/i18n` — signup, `RDynamic`, CRUD |
| `pnpm play:standalone` | **without** `@nuxtjs/i18n` — the module's own engine        |
| `pnpm play:ui`         | `--rf-*` tokens, `defineFieldDefaults`, per-field `ui`      |

Each playground proves a different axis under real-app conditions.
`standalone` is the only place the own engine runs, and `ui` the only one where
the theme is overridden.

## Tests

```bash
pnpm test          # vitest: unit + nuxt + e2e
pnpm test:types    # vue-tsc across the seven apps, plus the site's server/
pnpm lint          # oxlint
```

`test:types` runs **eight** `vue-tsc` passes: the module, the fixture, the site,
the four playgrounds, and the site's `server/`, where the [MCP](/en/support/mcp)
tools live — no `tsconfig.app.json` includes those. Each Nuxt app has its own
`.nuxt` and its own `#rform`, so checking one does not cover another.

## Conventions

- 4 spaces, double quotes, semicolons, `trailingComma: "none"`,
  `singleAttributePerLine: true`. That is `oxfmt.config.ts`.
- Comments and JSDoc in **pt-BR**; code in English (variable names, types, `ui`
  keys, `throw` messages).
- Short comments, and only where things are not obvious. The long rationale
  lives in `.claude/CLAUDE.md`.

## Careful with the theme test

`test/unit/theme.test.ts` tokenizes the **whole** `.vue` file, comments
included. A literal Tailwind class (`rounded-xl`, `bg-primary`) or a `(--rf-…)`
inside a comment **breaks the test**. An example in a component shows the tag,
never the class.

## Documentation

A page here is a `.md` in `docs/content/{pt,en}/`, and the two trees mirror each
other file by file — `test/unit/docs.test.ts` enforces the parity.

A demo is a real `.vue` in `docs/app/demos/<Component>/<id>.vue`, referenced by
`::demo{src="Component/id"}`. It goes through `vue-tsc` like any other file — and
the test also checks that every `src` cited in the content points at a file that
exists.

Two things here are **generated** from the source: the props table, and the JSON
the [MCP](/en/support/mcp) tools read. Two Nuxt modules in `docs/modules/` write
them on every `dev`, `build` and `prepare`, so they always match the source.
