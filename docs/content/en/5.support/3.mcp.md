Everything on this site is served a second time at **`/mcp`**, as an
[MCP](https://modelcontextprotocol.io) server. Point a code agent at it and it
reads the documentation instead of guessing at it.

## Why it exists

Whoever gets rform wrong most often is an agent, and it gets it wrong on things
this site already knows — but no `.d.ts` does:

- **The shape of the props.** A field's `Props` is an intersection
  (`Element<typeof defaults, "text"> & Utils["label"] & TextProp<…>`), so no
  readable declaration file lists them. The table on every field page is
  generated from the source by `vue-component-meta`, and `get-component-api`
  returns exactly that.
- **The shape of a preset's arguments.** They are **named in the ref itself** —
  `{ name: "min", min: 3 }`, never `args: [3]`, which is the shape agents reach
  for and which stopped compiling.
- **`label`, `placeholder`, `description` and `error` are `TrInput`**, not
  `string`. In an app with `@nuxtjs/i18n` a bare literal there is a compile
  error, and the fix is a key or a `~~` marker.

The server says all three in its `instructions`, so a client that forwards them
tells the agent before it writes the first line.

## Connecting

The endpoint speaks streamable HTTP over `POST`, and takes no authentication —
the documentation is public, and so is this.

```bash
claude mcp add --transport http rform https://<docs>/mcp
```

For a client configured by file — Cursor, VS Code, Windsurf, Zed — it is the
usual block:

```json
{
    "mcpServers": {
        "rform": {
            "type": "http",
            "url": "https://<docs>/mcp"
        }
    }
}
```

::callout{type="tip"}
`<docs>` is this site's own address: whatever is in your address bar, plus
`/mcp`.
::

## The tools

Six, and the optional argument is what keeps them from being ten — every `get`
also lists when you call it with nothing.

| tool                     | argument                      | what comes back                                                         |
| ------------------------ | ----------------------------- | ----------------------------------------------------------------------- |
| `search-documentation`   | `query`, `limit` (default 12) | ranked pages: path, title, snippet and the page's headings              |
| `get-documentation-page` | `path`                        | one page in full, raw markdown with its frontmatter                     |
| `list-documentation`     | —                             | every page: path, title, description, tag, headings                     |
| `get-component-api`      | `component`, optional         | props, slots and events of one of the 24 components — or the whole list |
| `get-demo`               | `name`, optional              | the source of one demo — or every demo name                             |
| `list-presets`           | `name`, `kind`, both optional | the 9 rules and 8 masks, and the source of one                          |

Two details that are not guessable:

- **`get-component-api` takes either form.** `"RText"` and `"Text"` both land on
  the field; `Calendar` is both a field and a util, so the bare name gives you
  the field and `"RUtilsCalendar"` reaches the other.
- **`list-presets` needs `kind` for a few names.** `brCpf` exists as a rule
  _and_ as a mask, and without `kind` you get both.

A path or a name that does not exist comes back as an error listing the valid
ones, so an agent that guesses wrong recovers in one more call.

## What it does not have

- **English only.** The tools read `content/en`; the Portuguese tree is not
  exposed. Paths therefore carry no locale prefix — the page for `/fields/text`
  is at `/en/fields/text` on the site.
- **Page granularity, not anchors.** Slicing by heading would mean replicating
  `@nuxt/content`'s heading slugs, and an agent wants the whole page anyway. Each
  hit carries the page's `headings` so you can see what is inside before reading
  it.
- **No resources and no prompts.** Tools only.
- **No authentication**, per the above.

## How it stays in sync

It is a **build artifact**, not a live query. A Nuxt module in `docs/modules/mcp`
reads `content/en`, `app/demos` and `src/runtime/presets` on every build and
writes one JSON that the tools read.

That is what makes the answers identical to the page: a demo goes through the
same `demoSourceOf` the site's code panel uses, so the source an agent gets is
byte-for-byte what you see here, and `get-component-api` serves the same
generated file the props tables render. It is also why the endpoint is cheap —
nothing queries the content database at runtime.
