`RArray`'s slot hands you `index`, and that is what the child uses as its
`name` — that is how the child's write lands in the right slot of the parent's
array.

## min and max

At `min` the remove button disappears; at `max` the add button does. And `min`
**seeds** the rows: the list never stays below it. Not only on mount — on a
reset, or when the model arrives short from the outside, the missing rows come in
empty, as through the add button. Neither prop becomes validation.

And they are optional when the `rule` already declares the limit: without the
prop, `RArray` reads the limit from its own `rule` — a preset or a zod schema
(see [rule](#rule), below). A prop you write wins, `:min="0"` included.

::demo{src="Array/min-max" title="min and max"}
::

Remove is a real `<button>`, at the end of each row: it is reachable with Tab,
has an `aria-label` (`text.remove`, below) and honors the field's `disabled`.

## Reordering

`sortable` turns on two ways of reordering, together or just one:

| value                               | what shows                    |
| ----------------------------------- | ----------------------------- |
| `false` (default)                   | nothing                       |
| `true`, or `sortable` with no value | the arrows **and** the handle |
| `"arrows"`                          | the arrows only               |
| `"drag"`                            | the handle only               |

Both land in the same place:

- **the arrows**, an up/down pair at the end of each row. Up is disabled on the
  first row, down on the last, and focus **follows the item**: after the click it
  sits on the same button of the row the item moved to, so you can carry an item
  from the bottom to the top just by pressing Enter again. This is the keyboard
  way;
- **the handle**, at the start of each row, to drag with a mouse or a finger. An
  indicator line shows where the item will land, `Escape` cancels midway, and
  dropping outside the list does not carry the item into another `RArray` — the
  target comes only from this list's rows.

::demo{src="Array/sortable" title="sortable"}
Submit with the second row empty, then move it, with the arrows or the handle:
the error goes along.
::

Dragging uses
[Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events),
not native HTML drag and drop, which does not fire on touch screens. The handle
carries `touch-action: none`, otherwise the browser would take the gesture to
scroll the page. It is `aria-hidden`: whoever does not use a pointer reorders
with the arrows — which is why `"drag"` alone leaves the list with no keyboard
reordering.

To set it for the whole app, use `defineFieldDefaults`; the tag still wins —
`:sortable="false"` turns a single field off, `sortable="arrows"` switches its
mode.

```ts
// app/rform/defaults.ts
import { defineFieldDefaults } from "#rform/utils";

export default defineFieldDefaults({
    Array: { sortable: "drag" }
});
```

The type of the four values is exported as `Sortable`, from the component itself:
`import type { Sortable } from "#rform/builtin/fields/Array.vue"`.

### The error follows the item

A child's error is keyed by the path with the index — `guests.2`,
`partners.1.id` (see [Errors from the outside](/en/form/form#errors-from-the-outside)).
When a row is removed or moved, `RArray` renumbers those keys, and the message
stays next to the item that caused it. Before, removing a row left the next
row's error parked at its position, pointing at another item.

The renumbering is done by `remapIndexKeys`, exported from `#rform/utils` —
useful if you reorder the model from the outside and want to carry an error map
along. The function returns the new index, or `null` to drop the key:

```ts
import { remapIndexKeys } from "#rform/utils";

// row 1 is gone: 2 becomes 1, and row 1's error is dropped
remapIndexKeys(errors, "items", (i) => (i === 1 ? null : i > 1 ? i - 1 : i));
```

::callout{type="warn"}
Only the **model** and the **error** follow the item. Each row is tied to its
index — a child's `id` is built once —, so a child's **local** state stays where
it was: an `RFile`'s in-flight upload queue, an `RSelect`'s open panel. Moving a
row in the middle of an upload leaves the progress bar at the old position.
::

## Animation

Adding, removing and moving animate through the
[View Transitions API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)
(`document.startViewTransition`). In a browser without it, or with
`prefers-reduced-motion: reduce`, the change is applied without animation.

The `view-transition-name`s only exist during the transition itself — always on,
they would also join your app's route transition. What stays fixed is the
class: every animated element carries `view-transition-class: rform-array`, and
that is what you customize, in global CSS:

```css
::view-transition-group(*.rform-array) {
    animation-duration: 150ms;
}
```

To turn it off, `animation: none` on the same selector.

::callout{type="warn"}
`<TransitionGroup>` is gone, and the `ui.list.transitionGroup` key with it.
Whoever passed it in `ui` or in `defineFieldDefaults` moves to the CSS above.
::

## text

`text` is a **nested** object mirroring the component's `defaults.text` — never
a flattened prop such as `buttonText`. What you pass goes in raw, without a
prefix: a key of your app, or a `~~` literal.

| key      | default                     | where it shows                      |
| -------- | --------------------------- | ----------------------------------- |
| `button` | `rform.fields.array.add`    | the add button's label              |
| `remove` | `rform.fields.array.remove` | the remove button's `aria-label`    |
| `up`     | `rform.fields.array.up`     | the move-up button's `aria-label`   |
| `down`   | `rform.fields.array.down`   | the move-down button's `aria-label` |

## rule

::demo{src="Array/rule" title="min and max over an array"}
`min` and `max` over an array become `z.array().min()` / `.max()` — again, the
schema comes from the value, not from the field type. And the buttons follow
those limits on their own: the list opens with 2 rows, the trash disappears at
2, add at 4, with no `:min`/`:max`. Over an array the message talks about
items: "At least 2 items."
::

The limit comes from three forms of `rule`, on their own or inside the array of
rules:

- the preset by reference — `{ name: "min", min: 2 }`, `{ name: "max", max: 4 }`;
- the [`schema` preset](/en/concepts/presets#json-schema-the-schema-preset), with
  the JSON Schema coming from the back end — `minItems` and `maxItems`;
- a [zod](https://zod.dev) schema — `z.array(...).min(2)`, `.max()`, `.length()`
  (becomes both minimum **and** maximum) and `.nonempty()` (minimum 1), going
  through `.optional()`, `.nullable()`, `.default()` and `.transform()`.

In an array mixing forms, the tightest limit wins: the largest minimum and the
smallest maximum. Left out are a `rule` in function form, which only yields the
number by running, and the `RForm`'s aggregated `:rules`, which never reaches
the field.

The direction is one way only, from the rule to the buttons: the `min`/`max`
prop validates nothing. The reader is `ruleLimits`, exported from
`#rform/utils`:

```ts
import { ruleLimits } from "#rform/utils";

ruleLimits([{ name: "min", min: 2 }, z.array(z.string()).max(4)]); // → { min: 2, max: 4 }
```

Schema mode (`RDynamic`, `useRForm`) works the same: the `rule` in a
`type: "array"` field's config reaches the `RArray`, and the buttons follow the
limit in all three forms.

## A note on performance

`RArray`'s `v-for` iterates `length` and passes each item through a row
component, instead of `v-for="(item, index) in model"`. That form read **every**
element in `RArray`'s own render, so one keystroke — a write to `array[i]` —
invalidated the whole list and repatched every sibling: 0.6 ms with 10 rows and
4.1 ms with 100, growing with the list where a flat form stayed flat.

Iterating `length` and passing `item` through a getter is not enough on its own:
`v-bind` on a `<slot>` normalizes the object and reads the getter all the same.
Only a component boundary scopes the dependency for real.

## Icons

Each role is a key of the `icons` prop, and the value is the iconify name. A
util's roles nest under `Utils`, as in `ui`:
`:icons="{ Utils: { Error: { alert: 'lucide:circle-alert' } } }"`. Layers,
`defineFieldDefaults` and the alias are in
[Icons](/en/concepts/icones#per-component-or-per-tag).

| role                | default                                         | where it shows                        |
| ------------------- | ----------------------------------------------- | ------------------------------------- |
| `add`               | `rform:plus` → `fa6-solid:plus`                 | on the add button, below the list     |
| `remove`            | `rform:trash` → `fa6-regular:trash-can`         | at the end of each row, to remove it  |
| `up`                | `rform:chevron-up` → `fa6-solid:chevron-up`     | with `sortable`, to move the row up   |
| `down`              | `rform:chevron-down` → `fa6-solid:chevron-down` | with `sortable`, to move the row down |
| `drag`              | `rform:grip` → `fa6-solid:grip-vertical`        | with `sortable`, the drag handle      |
| `Utils.Error.alert` | `rform:alert` → `ooui:alert`                    | next to the error message             |

## ui layers

The buttons of each row live in `list.item.actions`. `list.item.move` is the
class of the two move buttons, and `list.item.remove` the remove button's — both
are `<button>`s, so `focus-visible:` and `disabled:` apply there.

Dragging has four keys: `list.item.handle` is the handle; `list.item.dragging`
goes on the source row while it is dragged; `list.item.dropBefore` and
`list.item.dropAfter` draw the indicator, through `before:`/`after:` — which is
why `list.item.container` is `relative`. Dropping that `relative` knocks the
indicator out of place.
