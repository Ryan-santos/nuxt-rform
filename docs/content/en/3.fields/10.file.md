`RFile` has two modes, and the `upload` prop is what picks one. Without it, the
model keeps the browser's `File` object and your submit does the sending. With
it, the field uploads each file the moment the user picks it and the model keeps
whatever your function returned — an id, a URL — which is what a real form
stores.

::callout{type="info"}
This site runs `@nuxtjs/i18n`, so the demos pass a **translation key** instead of
text. In an app without i18n you would write `label="Attachment"` directly — see
[Translation](/en/concepts/traducao).
::

## The basics

`accept` is optional: absent, everything passes. Present, it becomes the input's
filter, the filter for whatever is dropped on the zone **and** the format badges.

::demo{src="File/basico" title="basics"}
Because a `File` serializes to `{}` in JSON, the panel beside it spells the file
out instead of lying that the field is empty.
::

## multiple

::demo{src="File/multiple" title="multiple"}
The model becomes a list. `multiple` works in its short form — no
`:multiple="true"` needed.
::

## accept

Three forms, and they mix in the same string: extension (`png`, `.png`), exact
MIME (`application/pdf`) and a family wildcard (`image/*`).

::demo{src="File/accept" title="extension, family and MIME"}
What the native input receives is the normalized form — `png` on its own does not
open the system dialog filtered, `.png` does.
::

## Limits

`maxSize` (in bytes) and `maxFiles` refuse a file **before** it goes up. The
refusal shows on that file's row, not in the field's `error`: `error` belongs to
the form, and validation is what writes it.

::demo{src="File/limites" title="maxSize and maxFiles"}
::

## API upload

The module owns the cycle — queue, progress, cancel, error, retry. The transport
is yours: a function, with no envelope convention and no dependency on `fetch`.

```ts
import type { Uploaded, UploadContext } from "#rform/types";

const upload = (file: File, { signal, onProgress }: UploadContext): Promise<Uploaded> => {
    // return at least { id, name, url }; the rest of the object passes through
};
```

| what               | who uses it                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| `signal`           | hand it to `fetch`/`XMLHttpRequest`: the cancel button is what fires it                                    |
| `onProgress(0..1)` | draws the row's bar. Calling it is optional                                                                |
| the return value   | becomes the model item. It needs `id`, `name` and `url`                                                    |
| `size` and `type`  | optional on the return: `size` becomes the size on the row, and `type` is what makes the thumbnail show up |
| a rejection        | leaves the row in error, with the `Error`'s message and a retry button                                     |

::demo{src="File/upload" title="progress, cancel and retry"}
The "server" here is a timer. Drop a file with **erro** in its name to watch the
row fail and the retry button show up.
::

`fetch` reports no upload progress; `XMLHttpRequest` does. If the bar matters,
that is the one — the demo above and the `upload` page of the `basic` playground
show both sides.

### The thumbnail

For a file uploaded **in this session** the thumbnail comes from the `File`
itself, with no second trip to the network. For one that came from the server it
comes from the `url` — and there `type` is what decides, because `/api/uploads/7`
has no extension to guess from.

### One default for the whole app

`upload` and `remove` are props like any other, so the place to standardize the
transport is `app/rform/defaults.ts` — and then no `RFile` in the app has to
repeat the function:

```ts
import { defineFieldDefaults } from "#rform/utils";

export default defineFieldDefaults({
    File: {
        upload: (file, { signal }) => send(file, signal),
        remove: (item) => $fetch(`/api/uploads/${item.id}`, { method: "DELETE" })
    }
});
```

A field can still pass its own function — a prop at the call site always beats
the default. To **not** use the default on one field, pass `false`:

```vue
<template>
    <RFile
        name="draft"
        :upload="false"
    />
</template>
```

::callout{type="warn"}
`:upload="undefined"` does not turn it off. The merge never lets an empty value
erase a default — that is the rule that keeps an absent prop from wiping what
`defaults.ts` set — which is why opting out needs a value of its own.
::

### Submit waits

An upload in flight is a race against the send button, and `RForm` is what
settles it: `validate()` and `submit()` wait for everything the field has in
flight to **settle** before looking at the model. An upload that failed does not
disappear quietly — it becomes an error message on the field, with the lowest
precedence of all, so a `rule` of yours still speaks first.

### remove

When an already-uploaded item leaves the list, the field calls the `remove` prop
with the object your upload function returned — that is where the DELETE lives.
If it rejects, the item **stays** and the reason shows on its row.

```vue
<template>
    <RFile
        name="attachments"
        multiple
        :upload="upload"
        :remove="(item) => $fetch(`/api/uploads/${item.id}`, { method: 'DELETE' })"
    />
</template>
```

## Slots

`#item` replaces the row; `#empty` replaces the middle of the dropzone. Neither
one wipes out the whole interface.

```vue
<template>
    <RFile
        name="attachments"
        multiple
    >
        <template #item="{ entry, retry, cancel, remove }">
            <p>{{ entry.name }} — {{ entry.status }}</p>
        </template>
    </RFile>
</template>
```

`entry` is the same shape in both modes: `{ key, name, size, file, url, type,
status, progress, message }`, with `status` being `done`, `pending`, `error` or
`rejected`.
