This page is the map from the inside. You do not need it to use the module — but
it explains why things behave the way they do, and it is what makes a field of
yours indistinguishable from a built-in one.

## A field is a component that calls `useField`

Every field — built in or yours — has the same shape:

```vue
<script lang="ts">
    import { useField } from "#rform/composables";
    import type { Element } from "#rform/types";
    import type Utils from "#rform/types/components/utils/props";
    import { defineDefaults } from "#rform/utils";

    export const defaults = defineDefaults({
        ui: { container: "flex grow flex-col gap-1" },
        default: ""
    });

    export type Props = Element<typeof defaults, "text"> & Utils["Label"];
</script>

<script setup lang="ts">
    const { id, model, props, tr, locale } = useField(defineProps<Props>());
</script>
```

Two script blocks, and the split is the contract:

- **`<script>`** exports `defaults` and the `Props` type. `defaults` is read
  from the outside — by the generated registry, by this documentation's layer
  tree, by the `Element` that types the props.
- **`<script setup>`** only calls the composable.

## What `useField` does

### 1. Finds the parent

It reads the `RForm` (or `RArray`/`RObject`) through `inject`. When there is a
parent **and** `props.name` is defined, `model.value` reads and writes
**directly** into `upper.model.value[name]`. That is why an array mutation in the
child's model shows up in the Form: there is no copy in between.

Without a parent, the field works the same — it just does not reach any model.

### 2. Merges the defaults

Four sources, in this order, through `merger` — and whoever comes later wins:

```
component defaults  →  app/rform/defaults.ts  →  local props  →  call-site props
```

That is why a prop on the field always beats the defaults file, which always
beats the component.

### 3. Seeds the `default`

And **clones** while seeding. `props.value.default` is the very object the
component declared at module scope — `merger` copies objects and arrays by
reference when the key exists in only one source. Handing it over raw let a child
write straight into it, polluting the default of every later instance in the
process.

### 4. Resolves `rule` and `mask`

**Masks** come from `#rform/masks`, imported statically: a mask is a literal
object, which is why the mask is already resolved on the first render.

**Rules** come from `#rform/presets`, imported **dynamically**, and only when the
field declares a `rule`. Every rule imports zod — a static import here would put zod
on the critical path of any page with a field, validated or not. The rule is
registered with the `RForm` right away; what waits for the chunk is the validation,
when it runs.

The field’s `rule` **returns** the message; what writes it into the field is
`RForm`, which merges each rule’s return with the issues of the aggregated
`:rules` and with whatever came from the outside into a single map. That is why
an error can show up on a field nobody touched.

## The utils are real components

`RUtilsLabel`, `RUtilsError`, `RUtilsPlaceholder`, `RUtilsLength`,
`RUtilsLoading`, `RUtilsDropdown`, `RUtilsCalendar` and `RUtilsDescription` are
`.vue` files the field mounts. They call `useUtil`, which reads the parent
field's props through injection — hence the `error` prop living on the field
while the message is drawn by the util.

The practical consequence: a util of **yours** in `app/rform/utils` contributes
props to every field that includes it. That is the mechanism, not an exception.

One of them leaves its place: the `RUtilsDropdown` panel — the one `RSelect`,
`RDate` and `RColor` open — is teleported to Nuxt's `#teleports`, outside the
field. That is what keeps a `transform` or an `overflow: hidden` on an ancestor
from shifting or clipping the dropdown. Its look is still the field's
`ui.Utils.Dropdown.popover`, and it still reads the `--rf-*` tokens, which live
on `:root`.

::callout{type="tip"}
`useField` and `useUtil` are **synchronous**, and that is the point: a field
renders six utils, and an async `setup` becomes a Suspense boundary and a
microtask hop before the subtree exists — paid even by the five utils that decide
to render nothing. What makes it possible is the build handing the `defaults` to
the call itself.
::

## The registry is generated

`module.ts` scans `src/runtime/components/{fields,utils}` and
`app/rform/{fields,utils}`, in built-in→user order — whoever comes later wins.
Out of that single scan come the types, the `components-map`, the `FieldType`, the
roots the Vite plugin rewrites, and `#rform/registry` — which now holds only the
names the build knows, so the composable can reject a component from outside it.

The `defaults` is not loaded at runtime: it reaches the call written by the
plugin, from the file's own `export const defaults`.

## The precedence is always the same

One rule, in five places:

| what      | weakest source                 | strongest source               |
| --------- | ------------------------------ | ------------------------------ |
| component | `src/runtime/components`       | `app/rform/fields`             |
| util      | `src/runtime/components/utils` | `app/rform/utils`              |
| preset    | `src/runtime/presets`          | `app/rform/presets`            |
| `ui`      | the component's `defaults`     | the `ui` prop at the call site |
| text      | prefixed `defaults.text`       | whatever you pass, raw         |

The exception is the **translation pack**: the same code **merges**, it does not
replace — that is what lets a three-key pack of yours still be complete.

## The theme uses no Tailwind token

No `ui` in the module uses a semantic token. Every color and every radius goes
through a variable of its own, as an arbitrary property:

```ts
container: "rounded-(--rf-radius-xl) bg-(--rf-color-background-100)";
```

There are 16 variables, and changing the theme is changing a variable. Details in
[Theme](/en/concepts/tema).

## The libraries doing the work

The module reimplements neither masking, validation nor positioning — it stitches
four libraries together and exposes one prop for each. When the question is about
how they behave, the answer is in their docs:

| library                                              | what it does here                                                        | prop            |
| ---------------------------------------------------- | ------------------------------------------------------------------------ | --------------- |
| [maska](https://beholdr.github.io/maska/)            | applies the mask and defines the tokens (`#`, `@`, `*`)                  | `mask`          |
| [zod](https://zod.dev)                               | is what the built-in rules _are_ — and `rule` takes a `ZodType` directly | `rule`          |
| [@floating-ui/vue](https://floating-ui.com/docs/vue) | positions the `RUtilsDropdown` panel — `flip`, `shift`, `size`           | —               |
| [vue-i18n](https://vue-i18n.intlify.dev)             | the message syntax, interpolation and plurals                            | `text`, `label` |

The full list, with each one's role, is in
[Compatibility](/en/support/compatibilidade#dependencies).
