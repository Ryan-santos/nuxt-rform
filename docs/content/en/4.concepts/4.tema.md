No `ui` in the module uses a Tailwind semantic token. Every color and every
radius goes through a variable of its own, as an _arbitrary property_:

```ts
container: "rounded-(--rf-radius-xl) bg-(--rf-color-background-100) has-[:focus]:outline-(--rf-color-primary)";
```

**Changing the theme is changing a variable — `ui` stays put.**

::callout{type="tip"}
The at-rules around this — `@theme`, `@layer`, `@source` and the `bg-(--var)`
_arbitrary property_ — are **Tailwind 4**'s, not rform's. The reference is the
[Tailwind theme docs](https://tailwindcss.com/docs/theme) and
[source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files).
::

## The 17 variables

| group      | variables                                                                            |
| ---------- | ------------------------------------------------------------------------------------ |
| background | `--rf-color-background`, `-100`, `-200`, `-300`                                      |
| text       | `--rf-color-contrast`                                                                |
| border     | `--rf-color-border`                                                                  |
| action     | `--rf-color-primary`, `--rf-color-primary-fg`                                        |
| state      | `--rf-color-danger`, `--rf-color-danger-fg`, `--rf-color-success`, `--rf-color-warn` |
| radius     | `--rf-radius-sm`, `-md`, `-lg`, `-xl`, `-2xl`                                        |

## They chain into your app's theme

Each default is a `var()` with a fallback:

```css
--rf-color-primary: var(--color-primary, #005bdf);
```

So an app that already has `primary` in its `@theme` **adopts it on its own** —
there is no override line to write. That is why this site needed none.

The `-100`/`-200`/`-300` steps (10%, 15%, 20%) are derived with `color-mix`
rather than chained: another app's `--color-background-100` might mean "a lighter
shade" instead of "10% toward the contrast".

`--rf-color-border` chains into `--color-border`, and its fallback is
translucent — `contrast` at 10% over `transparent` — rather than an opaque step:
the same border sits on `background` (the `RArray` group) and on `-100` (the
`RSelect` popover, the `RFile` dropzone), and a shade equal to `-100` would
vanish against its own surface. It is the **resting** border; the state ones
(`hover`, file uploaded, dragging) stay `primary` and `success`.

## How to override

Five forms, and the order of the two `@import`s only affects two of them:

| override form in the app                         | `#rform` first | `#rform` last |
| ------------------------------------------------ | -------------- | ------------- |
| `@theme { --rf-color-primary }`                  | works          | **ignored**   |
| `@layer base { :root { --rf-color-primary } }`   | works          | **ignored**   |
| `@layer rform { :root { --rf-color-primary } }`  | works          | works         |
| `:root { --rf-color-primary }` (outside a layer) | works          | works         |
| `@theme { --color-primary }` (chains)            | works          | works         |

The bottom three are immune to the order, each for a different reason: the same
layer resolves by declaration order (and the app comes later); a declaration
outside any layer beats every author layer; and `--color-primary` is one the
module **never** declares, so there is no conflict to resolve — it is just the
default's `var(--color-primary, …)` finding a value.

::callout{type="tip"}
The two natural forms — chaining through your app's `@theme`, or declaring
`--rf-*` inside `@layer rform` — work in **both** orders. What breaks is
declaring `--rf-*` **outside** `@layer rform` with `#rform` imported last — and
it breaks silently.
::

### Example, chaining

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@theme {
    --color-primary: oklch(0.6 0.2 250);
}
```

### Example, direct

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@layer rform {
    :root {
        --rf-color-primary: oklch(0.6 0.2 250);
        --rf-radius-xl: 0.25rem;
    }
}
```

## What stays literal, on purpose

- `*-current/*` — it is already `currentColor`.
- `bg-transparent`, `outline-transparent`.
- `rounded-{full,none,l-none,r-none}` — structural, not thematic.
- The hue `bg-[linear-gradient(…#f00…)]` in `RColor`.
- The `border-white` on the color picker markers — white **by design**, to
  contrast with an arbitrary color.

Note the asymmetry: `text-white` would be drift (it became `-fg`);
`border-white` is not.

## The icons

Color and radius are a variable; an icon is an **alias**. rform declares
`@nuxt/icon` as a module dependency and registers the 16 it uses under the
`rform:` namespace:

| group      | aliases                                                                     |
| ---------- | --------------------------------------------------------------------------- |
| action     | `rform:plus`, `rform:minus`, `rform:remove`, `rform:check`                  |
| navigation | `rform:select`, `rform:search`, `rform:chevron-left`, `rform:chevron-right` |
| state      | `rform:loading`, `rform:alert`                                              |
| file       | `rform:file`, `rform:image`, `rform:upload`, `rform:retry`, `rform:cancel`  |
| date       | `rform:calendar`                                                            |

**Swapping an icon is overriding the alias**, in `nuxt.config` — there is no field
prop to go looking for:

```ts
export default defineNuxtConfig({
    modules: ["nuxt-rform"],
    icon: {
        aliases: {
            "rform:calendar": "lucide:calendar",
            "rform:remove": "lucide:trash-2"
        }
    }
});
```

::callout{type="tip"}
Overriding one alias **does not take the other 15 down**: the Nuxt merge is deep,
key by key, and your value wins only on the key you wrote. Write one, the fifteen
stay standing.
::

The namespace is what keeps the two sides apart. The aliases used to be the short
names (`plus`, `calendar`…), and back then installing rform meant defining 16
aliases **in your app** — an `<Icon name="plus" />` on a page of yours resolved to
the icon the module picked, and a `calendar` alias of your own **replaced** the
`RDate` icon with nobody asking.

### Per instance, when that is what you want

The alias holds for the whole app. Two fields open a second door, which holds for
that one tag — and there the name is the raw iconify one:

```vue
<template>
    <RSwitch
        name="active"
        :icon="{ true: 'twemoji:check-mark-button', false: 'twemoji:cross-mark' }"
    />
</template>
```

The other is `RUtilsError`'s `ui.icon.name`, which is
[`ui`](/en/concepts/ui-e-defaults) like any other.

### In your own fields

In a `.vue` under `app/rform/fields` or `app/rform/utils` you write the iconify
name directly, as in any Vue component. But if the icon is one of the 16, call
`icon` from `#rform/utils`: besides not repeating the name, it **follows any
override** the app has made.

```vue
<template>
    <Icon :name="icon('alert')" />
    <Icon name="fa6-solid:star" />
</template>

<script lang="ts">
    import { icon } from "#rform/utils";
</script>
```

::callout{type="warn"}
A name that is not one of the 16 and has no `:` renders **nothing** — just an
`[Icon] failed to load icon` in the console. That is the failure mode to know: a
typo'd `icon("plux")` breaks neither the build nor lint, it erases the icon.
::

## The guard

`test/unit/theme.test.ts` covers five cases, and exists because of a failure mode
only a test can see: `bg-(--rf-color-primry)` — with the typo — compiles, passes
lint and renders `var(--undefined)`, that is transparent, **silently in every
environment**.

The five: (a) no raw semantic token came back; (b) the set of `--rf-*` used in
the components **equals** the declared set, in both directions; (c) the template
has exactly one absolute `@source` pointing at a directory that really contains
the components; (d) every token lives inside `@layer rform`; (e) `style.css` has
no Tailwind at-rule.

The icons have their own, `test/unit/icons.test.ts`, for the same reason: (a) the
set of names the components ask for **equals** the declared aliases, in both
directions; (b) no static name without a `:` was left in a template — which is
exactly what erased four icons when the namespace landed; (c) `icon()`'s prefix and
the module's short name are the same string.
