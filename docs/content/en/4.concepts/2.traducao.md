title: Translation

description: No text of the module is hardcoded, and every text you pass in a prop can be a key of your app.
---

rform has no text hardcoded in a component. Every message — the `RArray` button,
the `RFile` placeholder, a rule's error — comes out of a _message pack_, and
every text **you** pass in a prop (`label`, `placeholder`, `error`, `description`…)
can be a translation key of your app.

There are **two engines**, and the module picks one at build time:

| your app           | engine     | what happens                                                                                |
| ------------------ | ---------- | ------------------------------------------------------------------------------------------- |
| has `@nuxtjs/i18n` | **bridge** | rform registers its packs into the vue-i18n store under `rform` and uses your app's `$i18n` |
| does not           | **own**    | rform resolves on its own, with `@intlify/core`                                             |

There is no configuration for this. The detection is
`hasNuxtModule("@nuxtjs/i18n")`, and the body of the bridge engine **does not
write** the `@intlify/core` import — so an app with i18n does not pay its ~137 kB.
The cut is structural, not a bundler optimization that might fail.

::callout{type="tip"}
The message syntax is **vue-i18n**'s in both engines — `{param}` interpolation
and `a | b` plurals. The reference is the
[vue-i18n syntax docs](https://vue-i18n.intlify.dev/guide/essentials/syntax.html);
for `langDir`, `strategy` and the rest of the configuration rform reads, it is
[@nuxtjs/i18n](https://i18n.nuxtjs.org).
::

## `tr`, the one function

Every field and every util receives `tr` from the composables, with no import to
write:

```vue
<script setup lang="ts">
    const { props, tr } = useUtil<Props>();
</script>
```

It takes four shapes:

```ts
tr("form.name"); // a key of your app
tr({ key: "form.max", params: { n: 30 } }); // a key of your app, with params
tr("rform.formats.date"); // a module key, spelled out in full
tr("~~Name"); // an explicit literal
```

`tr` reads the locale on every call, so a call inside a template tracks the ref
and **switching languages re-renders** — including reformatting dates, because
the display format also comes from the pack.

### The algorithm

```
WITH THE BRIDGE                     WITHOUT IT
1. "~~…"  → strip the marker        1. "rform.…" → resolve in the module pack
2. rest   → $i18n.t(key)            2. rest      → return the string as is
```

::callout{type="warn"}
**The asymmetry is deliberate.** Without `@nuxtjs/i18n` there is nothing to
resolve an app key against, so `tr` is the identity — and `~~Name` literally
prints `~~Name`. A component written with an i18n app in mind carries that cost
in an app without one. It is accepted, not a bug.
::

## `TrInput`: the type is generated from **your** message file

Every text prop is typed as `TrInput`, and `TrInput` is **generated** from the
locale file your app declares in `@nuxtjs/i18n`.

```ts
// nuxt.config.ts
i18n: {
    defaultLocale: "en",
    langDir: "locales",
    locales: [
        { code: "en", name: "English", file: "en.json" },
        { code: "pt", name: "Português", file: "pt.json" }
    ]
}
```

```json
// i18n/locales/en.json
{
    "form": {
        "name": "Name",
        "max": "At most {n} characters",
        "items": "one item | {n} items"
    }
}
```

Out of that comes:

```ts
<RText label="form.name" />                             // ✅
<RText :description="{ key: 'form.max', params: { n: 30 } }" />  // ✅
<RText label="Name" />                                  // ❌ compile error
<RText label="~~Name" />                                // ✅ explicit literal
```

The generator reads the `defaultLocale` file, flattens it into dotted paths and
infers the parameters from the message text itself: `{n}` becomes `{ n: Interp }`,
a `|` becomes a plural choice (`number`), and both together become the union.

### The four modes

| situation                                       | `TrInput`                                         | why                                           |
| ----------------------------------------------- | ------------------------------------------------- | --------------------------------------------- |
| readable `.json`                                | `Paramless \| ModuleKey \| WithParams \| Literal` | full strictness                               |
| i18n with no `file` declared                    | `ModuleKey \| Literal`                            | no app key to offer, but the strictness stays |
| `file` in `.ts`, yaml, or a `lazy: true` loader | `string`                                          | plus a build warning naming the file          |
| no `@nuxtjs/i18n`                               | `string`                                          | there is no app i18n to respect               |

Only `.json` is read — it is `JSON.parse`, zero dependencies. The two
degradations are different on purpose: **no file** still demands a key or a
`~~`; **unreadable file** falls back to `string`, because being strict there
would reject every valid key.

## Overriding a module message

### With `@nuxtjs/i18n`

Declare the key under `rform` in **your** app's locale. It is vue-i18n's normal
precedence, with nothing specific to the module:

```json
{
    "rform": {
        "fields": { "array": { "add": "Add one" } },
        "presets": { "rules": { "required": "Please fill this in." } }
    }
}
```

### Without `@nuxtjs/i18n`

Create `app/rform/locales/<code>.ts`. **The same code merges**, it does not
replace — unlike a field, a util or a preset, where the same name swaps the whole
file. A three-key pack is still complete:

```ts
import { defineLocale } from "#rform/utils";

export default defineLocale({
    fields: {
        array: { add: "Add one" }
    }
});
```

A new code (`es`) simply joins; whatever is missing falls back to the default
pack. The initial language comes from the module option:

```ts
// nuxt.config.ts
rform: {
    locale: "pt-BR";
} // default
```

Without the bridge, the active locale is a `useState("rform-locale")` — write to
it to switch languages.

The `text` prop mirrors the component's `defaults.text`, nested — and what you
pass goes in raw, without a prefix.

## The module's key map

```
rform.
  fields.array.add
  fields.select.search
  fields.file.{placeholder,loading,zero,bytes.{b,kb,mb,gb,tb}}
  fields.date.{hint,hintTime,separator}
  fields.hour.{hint,separator}
  utils.calendar.{start,end,time}
  presets.rules.{required,email,url}
  presets.rules.min.{number,length}
  presets.rules.max.{number,length}
  presets.rules.br.{cpf,cnpj,cep,telefone}
  formats.date
```

`fields.*` and `utils.*` mirror `components/fields` and `components/utils`. That
is where the automatic prefix comes from — and it is what lets a field and a util
of the same name (`Calendar` is both) coexist.

`formats.date` is not text: it is the pattern (`DD/MM/YYYY`) from which the mask,
the parse regex and the display formatting are derived. Translating it is how
`RDate` changes format per language.

## Writing a translatable field or util

Declare the keys in `defaults.text` and derive the props with `TextProp`:

```vue
<template>
    <button>{{ tr(props.text?.button) }}</button>
</template>

<script lang="ts">
    export const defaults = defineDefaults({
        ui: { container: "flex flex-col gap-1" },
        default: [],
        text: {
            button: "add"
        }
    });

    export type Props = Element<typeof defaults, "array"> &
        Utils["Label"] &
        TextProp<typeof defaults.text>;
</script>
```

Three things happen on their own:

1. **The value is prefixed** with `rform.fields.<component>.` (or
   `rform.utils.<name>.` in a util), so `"add"` becomes `rform.fields.array.add`.
2. **`TextProp` generates the prop's type** — `{ text?: { button?: TrInput } }`.
   You do not restate the keys.
3. **Whoever passes the prop wins**, raw. The prefixing happens _before_ the
   merge, so provenance comes for free:

```ts
<RArray :text="{ button: 'form.add' }" />                    // → "form.add"  (raw)
defineFieldDefaults({ Array: { text: { button: "my.add" } } }) // → "my.add"  (raw)
// nothing passed                                            // → "rform.fields.array.add"
```

### Nested groups

The group joins the path, so the tree mirrors the pack:

```ts
text: {
    loading: "loading",
    bytes: { kb: "kb", mb: "mb" }
}
// → rform.fields.file.loading, rform.fields.file.bytes.kb, …
```

And `TextProp` follows:

```ts
TextProp<{ hint: string; test: { a: string } }>;
// → { text?: { hint?: TrInput, test?: { a?: TrInput } } }
```

### `label` and `placeholder` stay **outside** `text`

They are props the app passes directly, by contract, so they live at the top:

```ts
export const defaults = defineDefaults({
    ui: { … },
    default: null,
    placeholder: "placeholder",   // ← top level, not inside text
    text: { loading: "loading" }
});
```

A value the **component** declared there is still a module message, so it is
prefixed too (`rform.fields.file.placeholder`). An empty string is the sentinel
for "render nothing" and passes through untouched.

### Naming keys

Do not repeat "text" inside `text`: `text: { buttonText }` is noise,
`text: { button }` is right — the read path already says it
(`props.text.button`).

## Rules

A rule is not a component and cannot call a composable, so it **imports** the
translator:

```ts
import { defineRule, trRule, type RuleContext } from "#rform/utils";

export default defineRule({
    validation: ({ value, min }: RuleContext<{ min: number }>) =>
        value.length >= min ? undefined : trRule({ key: "min.length", params: { min } })
});
```

`trRule` is just sugar: it prefixes `rform.presets.rules.`. For a message from
**your app**, use `tr` directly — it takes the full path.

A validation's context is `{ value, form, ...args }` and nothing else.

### Plural

The `min`/`max` messages are real plurals:

```ts
"At least {min} character. | At least {min} characters.";
```

A **number inside the named parameters chooses the form**, so the call site does
not repeat the value: `trRule({ key: "min.length", params: { min: 1 } })` gives
"At least 1 character." and `{ min: 5 }` gives "…5 characters.".

::demo{src="Traducao/rules" title="a rule message, and a real plural"}
Hit submit: `min 1` says "character" and `min 5` says "characters".

## Gotchas

### A literal `@` needs escaping

`@:key` is vue-i18n's _linked message_ syntax. A raw e-mail inside a message
takes the parser down:

```
Invalid linked format (error code: 10)
target message: you@company.com
target message path: form.emailExample
```

Write `{'@'}`:

```json
{ "emailExample": "you{'@'}company.com" }
```

The type generator strips the literal `{'…'}` interpolations **before** looking
for parameters, so the escape does not invent a parameter named `@`.

::demo{src="Traducao/arroba" title="the escaped placeholder"}
::

### The app's locale owns the language list

The bridge registers the module's packs **under the codes your app declared**,
picking by exact code and, failing that, by language. An app with
`locales: ["pt", "es"]` still has `["pt", "es"]`: `pt` gets the `pt-BR` pack,
`es` gets nothing and falls back to vue-i18n's `fallbackLocale`.

That is deliberate — registering a code the app did not declare would make it
appear in its own language switcher, in `localeCodes` and in the prerender.

### What is **not** translated

The model. `formatIso*` and the ISO branch of `parseIncoming` are
language-independent by definition: localizing them would make the stored value
change with the language on screen. Only the _display_ follows `formats.date`.

### Cost without i18n

In an app **without** `@nuxtjs/i18n`, `@intlify/core` enters the bundle: ~137 kB
(`core-base` 66 kB + `message-compiler` 57 kB + `shared` 14 kB). In an app
**with** it, zero — the bridge uses the vue-i18n already there.

`@intlify/core` is a `dependencies` entry, not an optional peer: the path without
i18n is the common one, and an optional peer would make the default case require
a manual install.
