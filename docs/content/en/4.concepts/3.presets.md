One file = one preset. The name comes from the relative path in camelCase:
`br/insc-est.ts` becomes `brInscEst`.

- **Built in:** `src/runtime/presets/{rules,masks}/**/*.ts`.
- **Yours:** `app/rform/presets/{rules,masks}/**/*.ts`, recursive. **The same
  name overrides the built-in one.**

## Masks

Everything Brazil-specific lives under `br/` and becomes `brSomething`. There is
no generic mask today.

::demo{src="Presets/masks" title="the eight built-in masks"}
::

A name that matches no preset goes straight to
[maska](https://beholdr.github.io/maska/) as a raw pattern.

::callout{type="tip"}
The one applying the mask is [maska](https://beholdr.github.io/maska/): the
tokens (`#` digit, `@` letter, `*` both), `reversed`, `eager` and the rest of
the `defineMask` options are theirs, and their docs apply here untranslated.
::

## Rules

Generic ones at the root (`required`, `min`, `max`, `email`, `url`) and the
Brazilian ones under `br/`.

::demo{src="Presets/rules" title="the built-in rules"}
Hit submit.
::

::callout{type="tip"}
The built-in rules **are** zod: each one builds a schema and returns the first
issue as the message. And `rule` takes a `ZodType` directly — so everything the
[zod](https://zod.dev) docs describe works as validation here.
::

### Args named in the ref itself

They are not positional:

```ts
rule="min"                              // preset with no required arg
:rule="{ name: 'min', min: 3 }"         // with an arg
:rule="{ name: 'brInscEst', uf: 'SP' }" // your preset, with an arg
```

The args' type comes from the `validation`'s own parameter, so:

- a preset with no args → takes `"min"` and `{ name: "min" }`;
- a preset with a required arg → **only** `{ name, ...args }`, and missing it or
  getting its type wrong is a compile error.

### min and max pick the schema from the **value**

Not from the field type: with a number in the model they become
`z.number().min()`, with an array `z.array().min()`, with a string
`z.string().min()`.

## Writing your own

```ts
// app/rform/presets/masks/dinheiro.ts
import { defineMask } from "#rform/utils";

export default defineMask({
    mask: "R$ ###.###,##",
    reversed: true
});
```

```ts
// app/rform/presets/rules/br/insc-est.ts
import { defineRule, type RuleContext } from "#rform/utils";

export default defineRule({
    available: ["text"],
    validation({ value, uf }: RuleContext<{ value: string; uf: string }>) {
        if (!value) {
            return;
        }

        if (value.length < 9) {
            return `Invalid state registration for ${uf}.`;
        }
    }
});
```

::demo{src="Presets/usuario" title="both in use"}
::

The helpers come from `#rform/utils` and are **not** auto-imported — import them
explicitly.

### available

`available` is `readonly FieldType[]`, so `["txt"]` fails at the definition with
_Did you mean `"text"`?_ instead of never matching any component. It is the
filter that decides which fields the preset shows up on.

### The context is a single object

Every validation — from a preset **or** an inline function in `rule` — receives
`{ value, form, ...args }` and nothing else. `RuleContext` is what types it:

```ts
RuleContext; // { value: unknown, form: … }
RuleContext<{ uf: string }>; // plus the arg
RuleContext<{ value: string }>; // narrows value: unknown & string = string
```

The translator is **not** in the context: a rule reaches the active locale
through the imported `trRule`. See
[Translation](/en/concepts/traducao#rules).

::callout{type="warn"}
`fromPreset` builds the context as `{ ...args, value, form }` — in that order on
purpose, so an arg named `value` or `form` cannot shadow what the field actually
has.
::

## Colliding names

Two paths that collapse into the same name (`br/cpf.ts` + `brCpf.ts`) make the
build speak up: `ERROR [rform] duplicate preset name`, naming both files. Nuxt
downgrades a template failure to a warning, so `prepare` still exits 0 — the
symptom is the generated file disappearing, not the build stopping. A **mask**
collision does stop the build: the module imports `#rform/masks` statically.

## A preset in useRForm

A preset passes untouched through `normalizeSchema` (the field is what resolves
it) and becomes `z.any().superRefine(async …)` in the aggregated `rules`. That is
why **a schema with a preset requires `safeParseAsync`**; a zod-only schema stays
synchronous.

In practice `safeParseAsync` stopped being the app’s job: hand `rules` to
[`<RForm :rules>`](/en/form/form) and every issue lands on the field that owns
it.
