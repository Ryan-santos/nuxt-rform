`RFile` tem dois modos, e quem decide é a presença da prop `upload`. Sem ela, o
model guarda o objeto `File` do browser e quem envia é o seu submit. Com ela, o
campo envia cada arquivo assim que o usuário o escolhe e o model guarda o que a
sua função devolveu — um id, uma URL — que é o que um formulário de verdade
grava.

::callout{type="info"}
Este site roda com `@nuxtjs/i18n`, então os demos passam **chave de tradução**
em vez de texto. Num app sem i18n você escreveria `label="Anexo"` direto — veja
[Tradução](/pt/concepts/traducao).
::

## O básico

`accept` é opcional: ausente, tudo passa. Presente, ele vira o filtro do input,
o filtro de quem é solto na dropzone **e** as badges de formato.

::demo{src="File/basico" title="básico"}
Como um `File` serializa para `{}` em JSON, o painel ao lado o imprime por
extenso em vez de mentir que o campo está vazio.
::

## multiple

::demo{src="File/multiple" title="multiple"}
O model vira uma lista. `multiple` funciona na forma curta — sem `:multiple="true"`.
::

## accept

Três formas, e elas se misturam na mesma string: extensão (`png`, `.png`), MIME
exato (`application/pdf`) e curinga de família (`image/*`).

::demo{src="File/accept" title="extensão, família e MIME"}
O que o input nativo recebe é a forma normalizada — `png` sozinho não abre o
diálogo do sistema filtrado, `.png` abre.
::

## Limites

`maxSize` (em bytes) e `maxFiles` recusam **antes** de subir. A recusa aparece
na linha do arquivo, não no `error` do campo: o `error` é do formulário, e quem
o escreve é a validação.

::demo{src="File/limites" title="maxSize e maxFiles"}
::

## Upload por API

O módulo é dono do ciclo — fila, progresso, cancelar, erro, tentar de novo. O
transporte é seu: uma função, sem convenção de envelope e sem dependência de
`fetch`.

```ts
import type { Uploaded, UploadContext } from "#rform/types";

const upload = (file: File, { signal, onProgress }: UploadContext): Promise<Uploaded> => {
    // devolve no mínimo { id, name, url }; o resto do objeto passa intacto
};
```

| o que              | quem usa                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------- |
| `signal`           | passe ao `fetch`/`XMLHttpRequest`: é ele que o botão de cancelar dispara                    |
| `onProgress(0..1)` | desenha a barra da linha. Chamar é opcional                                                 |
| o retorno          | vira o item do model. Precisa ter `id`, `name` e `url`                                      |
| `size` e `type`    | opcionais no retorno: o `size` vira o tamanho na linha, e o `type` faz a miniatura aparecer |
| uma rejeição       | deixa a linha em erro, com a mensagem do `Error` e o botão de tentar de novo                |

::demo{src="File/upload" title="progresso, cancelar e tentar de novo"}
O "servidor" aqui é um timer. Solte um arquivo com **erro** no nome para ver a
linha falhar e o botão de tentar de novo aparecer.
::

`fetch` não reporta progresso de envio; `XMLHttpRequest` reporta. Se a barra
importa, é ele — o demo acima e a página `upload` do playground `basic` mostram
os dois lados.

### A miniatura

De um arquivo que subiu **nesta sessão** a miniatura sai do próprio `File`, sem
uma segunda ida à rede. De um que já veio do servidor ela sai da `url` — e aí o
`type` é o que decide, porque `/api/uploads/7` não tem extensão para adivinhar.

### Um padrão para o app inteiro

`upload` e `remove` são props como quaisquer outras, então o lugar de padronizar
o transporte é o `app/rform/defaults.ts` — e aí nenhum `RFile` do app precisa
repetir a função:

```ts
import { defineFieldDefaults } from "#rform/utils";

export default defineFieldDefaults({
    File: {
        upload: (file, { signal }) => enviar(file, signal),
        remove: (item) => $fetch(`/api/uploads/${item.id}`, { method: "DELETE" })
    }
});
```

Um campo continua podendo passar a própria função — prop no call site sempre ganha
do default. Para **não** usar o padrão em um campo, passe `false`:

```vue
<template>
    <RFile
        name="rascunho"
        :upload="false"
    />
</template>
```

::callout{type="warn"}
`:upload="undefined"` não desliga. O merge nunca deixa um valor vazio apagar um
default — é a regra que faz prop ausente não zerar o que o `defaults.ts` definiu —
e é por isso que a recusa precisa de um valor próprio.
::

### O submit espera

Um upload em voo é uma corrida contra o botão de enviar, e é o `RForm` quem a
resolve: `validate()` e `submit()` esperam a **liquidação** de tudo que o campo
tem em voo antes de olhar o model. Um upload que falhou não some calado — ele
vira mensagem de erro no campo, com a menor precedência de todas, então uma
`rule` sua continua falando primeiro.

### remove

Ao tirar da lista um item que já subiu, o campo chama a prop `remove` com o
objeto que a sua função de upload devolveu — é onde mora o DELETE. Se ela
rejeitar, o item **fica** e o motivo aparece na linha.

```vue
<template>
    <RFile
        name="anexos"
        multiple
        :upload="upload"
        :remove="(item) => $fetch(`/api/uploads/${item.id}`, { method: 'DELETE' })"
    />
</template>
```

## Slots

`#item` troca a linha; `#empty` troca o miolo da dropzone. Nenhum dos dois apaga
a interface inteira.

```vue
<template>
    <RFile
        name="anexos"
        multiple
    >
        <template #item="{ entry, retry, cancel, remove }">
            <p>{{ entry.name }} — {{ entry.status }}</p>
        </template>
    </RFile>
</template>
```

O `entry` é a mesma coisa nos dois modos: `{ key, name, size, file, url, type,
status, progress, message }`, com `status` em `done`, `pending`, `error` ou
`rejected`.
