`RSelect` aceita `options` em três formatos e decide sozinho o que vira valor e
o que vira rótulo. Compare no painel de model: sem `modelFull` o model guarda só
o valor; com `modelFull` guarda o objeto inteiro.

## options

### Array primitivo

O valor e o rótulo são o próprio item.

::demo{src="Select/primitivo" title="array primitivo"}
::

### Objeto `{ chave: rótulo }`

A chave vira o valor; o valor do objeto vira o rótulo. O que vai pro model é a
chave.

::demo{src="Select/objeto" title="objeto"}
::

### Array de objetos

`pick` diz quais campos do item viram o valor e o rótulo. Ele tem default no
`defaults` do componente (`{ value: "id", label: "name" }`) — e fica **fora** de
`defaults.text` justamente porque não é texto: se estivesse lá dentro, o
auto-prefixo o transformaria em `rform.fields.select.id`, e o Select passaria a
procurar `option["rform.fields.select.id"]`.

O `merger` mescla folha a folha, então `:pick="{ value: 'codigo' }"` conserva o
`label: "name"` do default — sobrescrever uma das duas chaves não apaga a outra.

::demo{src="Select/pick" title="pick"}

## search

`search` põe um campo de busca no topo do painel, filtrando as opções pelo
rótulo. É opt-in — numa lista de três itens a busca é ruído.

::demo{src="Select/search" title="busca dentro do painel"}
::

`defineFieldDefaults({ Select: { search: true } })` liga a busca no app inteiro.
Ligada assim, ela **não** se desliga num campo só: a regra "não apaga" do
`merger` pula quando o resultado é truthy e o valor novo é falsy, então o `true`
do app vence o `:search="false"` da tag.

### @search: buscar no servidor

`@search` reporta o termo a cada tecla. Quem escuta **assume o filtro**: o campo
para de filtrar a lista sozinho e passa a mostrar exatamente as `options` que
chegarem. Ele liga o campo de busca sozinho — `search` ao lado é redundante.

::demo{src="Select/busca-remota" title="a lista vem de fora"}
O servidor casa o termo com o nome e com a UF. Digite `BA`.
::

Não é conveniência: filtrar de novo do lado do cliente **esconderia** o que o
servidor casou por um campo que não é o rótulo. Uma cidade da Bahia não tem "BA"
no nome, e um contato achado pelo telefone some da lista enquanto se digita o
telefone.

O debounce fica de fora de propósito — quanto esperar depende da rota que
responde, não do componente que digita. `loading` é a prop de sempre.

`@search` é **relatório**: ele reporta o termo e mais nada. Quando é o campo que
deve buscar e paginar, o que se passa é uma função em `options` — a seção
seguinte.

## options como função

`options` também aceita uma função. Aí quem busca é o app, e o módulo passa a ser
dono do **ciclo**: debounce, número da página, fim da lista, erro com retry e o
rótulo do que já está escolhido.

```ts
const buscar = ({ search, page, signal }) =>
    $fetch("/api/usuarios", { query: { search, page }, signal });
```

::demo{src="Select/remoto" title="carrega rolando"}
500 nomes, 20 por página. Role até o fim da lista para a próxima chegar.
::

O contexto que a função recebe:

| chave | o quê |
|---|---|
| `search` | o termo digitado, já com o debounce aplicado |
| `page` | **1-based**. A página 1 é o primeiro `open`, e cada rolada até o fim pede a seguinte |
| `loaded` | o que já está na lista, para quem prefere paginar pelo último item |
| `value` | o model do campo |
| `form` | o model do `RForm` inteiro |
| `signal` | um `AbortSignal` — a requisição obsoleta é abortada |

**Array vazio encerra.** Não há envelope a montar nem cursor a devolver: a função
devolve a página, e uma página vazia diz que acabou. Uma página que não faz a
lista crescer encerra também — é a guarda contra a função que ignora `page` e
devolve sempre o mesmo, cujo sintoma seria o navegador travando.

O debounce é a prop `debounce`, em milissegundos, com default `300`. `0` desliga.

**Ela não liga a busca sozinha**, ao contrário do `@search`: uma lista infinita
sem termo nenhum é uso legítimo, e ligar o campo de busca ali seria surpresa.
Escreva `search` quando quiser os dois.

Com `options` em função o filtro local **desiste** — a lista que voltou já é a
resposta ao termo. É a mesma razão do `@search`, pelo mesmo motivo.

### O rótulo do escolhido não sai da tela

Esta é a diferença que importa em relação ao `@search`. O campo guarda o rótulo
do que foi escolhido, então digitar na busca, paginar e reabrir o painel não
apagam o nome que está no campo — e não é preciso concatenar o selecionado ao
resultado como o `@search` exige.

O cache guarda só o que foi **escolhido ou resolvido**, nunca a lista: ele é
limitado pelo número de seleções, não pelo número de buscas.

### A seção do selecionado

Em modo remoto o que está escolhido sobe para um bloco fixo no topo do painel,
fora da lista que rola. O ponto é não perder de vista a seleção **enquanto se
pagina** — no topo da lista ela sumiria na primeira rolada, que é exatamente
quando ela serve.

A busca não a filtra, e a linha é a mesma linha: mesmo slot, mesmo clique, e em
`multiple` clicar desmarca. Com `multiple` e muitas seleções ela para de crescer
e rola por dentro; a altura é a chave `ui.list.pinned`, que é o que um app com
seleção larga vai querer trocar:

```vue
<RSelect
    :options="buscar"
    multiple
    :ui="{ list: { pinned: 'max-h-72' } }"
/>
```

Em modo estático a seção não existe: ali o escolhido já está na lista e sempre
esteve, e subi-lo reordenaria a lista de quem nunca pediu nada disso.

### Estados

Carregando, vazio e erro têm lugar próprio. A primeira página ocupa o lugar da
lista; a próxima, uma faixa no rodapé. Falha ao carregar **não** é falha de
validação — ela nunca vira o `error` do campo, que tem um escritor só.

Os dois slots novos são `empty`, no lugar da lista, e `footer`, na faixa abaixo
dela — este recebe `status` e `retry`, porque erro de rede sem botão é beco sem
saída.

## resolve

Numa tela de edição o model já chega preenchido, e o valor dele pode não estar na
primeira página. `resolve` traduz o valor no item:

```ts
const traduzir = ({ value, signal }) =>
    $fetch(`/api/usuarios/${value}`, { signal }).then((usuario) => [usuario]);
```

::demo{src="Select/resolve" title="abre preenchida"}
O `default` é o id 317, que não está na primeira página.
::

Ela roda uma vez por chave desconhecida — inclusive quando o model muda por fora,
num reset do formulário ou num `carregar(id)` de CRUD —, e o que ela devolve
alimenta **só** o cache de rótulos, nunca a lista: um item resolvido aparecendo no
painel seria duplicata.

Ela **não** roda com `options` estática (ali "não está na lista" é "não existe"),
nem com o model vazio, nem para uma chave que a página ou o cache já respondem —
então escolher pela UI nunca dispara requisição.

::callout
**Com `modelFull` você não precisa de `resolve`.** O model já é o objeto inteiro,
e o rótulo sai dele pelo `pick.label` — sem cache, sem requisição e sem o piscar
do valor cru. É a rota barata para tela de edição.
::

Como qualquer prop-função, `resolve` aceita `false` para recusar o que um
`defineFieldDefaults` padronizou para o app inteiro.

## Lista longa

Acima de 100 linhas o painel passa a renderizar só a janela visível. Liga sozinho
— não há prop a escrever:

::demo{src="Select/virtual" title="5.000 opções"}
Abra o inspetor: o painel tem ~20 filhos, não 5.000.
::

O `@tanstack/vue-virtual` viaja num chunk à parte, carregado só quando a lista
cruza o limiar — um app que nunca renderiza 20 opções não paga por ele no bundle.

A troca é monotônica dentro de uma abertura: uma vez virtualizada a lista
continua assim até o painel fechar, porque alternar a estratégia a cada tecla é
jitter de scroll e de foco.

`rowHeight` (default `48`) é a altura estimada de uma linha, e só governa a barra
de rolagem antes da primeira medição — as linhas são medidas de verdade depois
do primeiro render, que é o que deixa o slot livre funcionar.

## Tipagem

O generic de `options` chega até o valor. `modelValue`, `default`, o payload de
`@update:model-value` e o `value`/`label` do slot saem do tipo que você passou —
não há cast a fazer nem `find` na lista para reaver o que o componente já sabia.

```vue
<RSelect
    :options="users"
    :pick="{ value: 'id', label: 'name' }"
    @update:model-value="onlyNumber"
/>
```

Com `users: { id: number, name: string }[]`, o payload é `number`. Com
`model-full`, é o objeto inteiro; com `multiple`, a lista de um ou de outro.

| `options` | `value` | `label` |
|---|---|---|
| array de primitivos | o próprio item | o próprio item |
| array de objetos | `item[pick.value]` | `item[pick.label]` |
| objeto | a chave | o valor, ou `valor[pick.label]` |

`pick.value` e `pick.label` sugerem as chaves do item, mas **não** fecham nelas:
o `getProperty` resolve caminho pontilhado, e `:pick="{ value: 'user.id' }"`
continua válido. Um caminho desses não é `keyof`, então ali o valor volta a ser
`unknown` — que é o que todos os casos eram antes.

::callout{type="warn"}
Escreva o `pick` **inline**. A inferência anda por propriedade, então
`:pick="{ value: 'id' }"` na tag preserva o literal; uma variável de objeto
alarga para `string` e o campo deixa de compilar, reclamando de `"id"` — que é
o default, não a sua chave. A saída é `as const`:

```ts
const pick = { value: "codigo", label: "descricao" } as const;
```
::

## Altura do painel

O painel abre com no máximo `25rem` de altura — o `max-h-100` — e rola por
dentro; numa viewport menor que isso ele encolhe para o espaço livre, virando
para cima quando embaixo não cabe. O teto é a variável `--max-height`, e trocá-lo
é uma arbitrary property no `popover`, por campo ou pelo `defineFieldDefaults`:

```vue
<RSelect
    :options="options"
    :ui="{ Utils: { Dropdown: { popover: '[--max-height:30rem]' } } }"
/>
```

`[--max-height:100vh]` tira o teto e deixa só o ajuste à viewport.
