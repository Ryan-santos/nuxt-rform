## O que muda com `@nuxtjs/i18n`

Instalá-lo troca o motor de tradução **em tempo de build**, sem configuração:

|                 | sem `@nuxtjs/i18n`            | com                                  |
| --------------- | ----------------------------- | ------------------------------------ |
| motor           | `@intlify/core` próprio       | ponte para o `$i18n` do app          |
| custo no bundle | ~137 kB                       | **zero**                             |
| `TrInput`       | `string`                      | união estreita gerada do seu `.json` |
| `~~Nome`        | imprime `~~Nome`              | imprime `Nome`                       |
| pack do usuário | `app/rform/locales/<code>.ts` | chave `rform` no locale do app       |

A detecção é `hasNuxtModule("@nuxtjs/i18n")`, que lê a lista **declarada** de
módulos — então não depende de o rform ser registrado antes ou depois do i18n.

## O que muda com Tailwind

Sem Tailwind, nada emite as classes do módulo. Use `css: ["nuxt-rform/style.css"]`, o
CSS já construído que o pacote exporta.

## SSR

Suportado. Todos os campos renderizam no servidor.

Três detalhes valem nota:

- Os blocos de código deste site usam `data-allow-mismatch`, porque o realce é
  gerado por string.
- O `RUtilsDropdown` posiciona no cliente (é layout), então o painel só mede
  depois da hidratação.
- O seletor de tema também usa `data-allow-mismatch`: o valor vem do
  `localStorage`, que o servidor não tem.

## Acessibilidade

O que já está: `aria-required` vindo de `required`, `label` real associado ao
input, `role="radiogroup"` nos seletores de opção, navegação por teclado no
`RPin` e no `RSelect`.

## Browsers

Os alvos padrão do Nuxt 4. O CSS usa `color-mix()`, `light-dark()` e `:has()` —
todos com suporte amplo desde 2023/2024. O reset de autofill depende de
`:-webkit-autofill`, que Chrome, Safari e Firefox 86+ implementam.
