Tudo o que está neste site é servido uma segunda vez em **`/mcp`**, como um
servidor [MCP](https://modelcontextprotocol.io). Aponte um agente de código para
lá e ele passa a ler a documentação em vez de chutar.

## Por que existe

Quem mais erra o rform é agente, e erra no que este site já sabe — mas nenhum
`.d.ts` sabe:

- **A forma dos props.** O `Props` de um campo sai de uma interseção
  (`Element<typeof defaults, "text"> & Utils["label"] & TextProp<…>`), então não
  há arquivo de declaração legível que os liste. A tabela de toda página de campo
  é gerada do fonte pelo `vue-component-meta`, e é exatamente ela que o
  `get-component-api` devolve.
- **A forma dos args de um preset.** Eles são **nomeados no próprio ref** —
  `{ name: "min", min: 3 }`, nunca `args: [3]`, que é a forma que o agente tenta
  e que deixou de compilar.
- **`label`, `placeholder`, `description` e `error` são `TrInput`**, não
  `string`. Num app com `@nuxtjs/i18n` um literal solto ali é erro de
  compilação, e a saída é uma chave ou o marcador `~~`.

O servidor diz as três coisas nas `instructions` dele, então um cliente que as
repassa avisa o agente antes da primeira linha.

## Conectando

O endpoint fala streamable HTTP por `POST`, e não pede autenticação — a
documentação é pública, e ele também.

```bash
claude mcp add --transport http rform https://<docs>/mcp
```

Num cliente configurado por arquivo — Cursor, VS Code, Windsurf, Zed — é o bloco
de sempre:

```json
{
    "mcpServers": {
        "rform": {
            "type": "http",
            "url": "https://<docs>/mcp"
        }
    }
}
```

::callout{type="tip"}
`<docs>` é o endereço deste site: o que estiver na sua barra de endereços, mais
`/mcp`.
::

## As ferramentas

São seis, e o argumento opcional é o que impede que virem dez — todo `get`
também lista, quando chamado sem nada.

| ferramenta               | argumento                         | o que volta                                                                 |
| ------------------------ | --------------------------------- | --------------------------------------------------------------------------- |
| `search-documentation`   | `query`, `limit` (padrão 12)      | páginas ranqueadas: caminho, título, trecho e os títulos internos da página |
| `get-documentation-page` | `path`                            | uma página inteira, markdown cru com o frontmatter                          |
| `list-documentation`     | —                                 | toda página: caminho, título, descrição, tag, títulos                       |
| `get-component-api`      | `component`, opcional             | props, slots e eventos de um dos 24 componentes — ou a lista inteira        |
| `get-demo`               | `name`, opcional                  | o fonte de um demo — ou o nome de todos                                     |
| `list-presets`           | `name`, `kind`, os dois opcionais | as 9 rules e 8 masks, e o fonte de uma                                      |

Dois detalhes que não se adivinham:

- **O `get-component-api` aceita as duas formas.** `"RText"` e `"Text"` caem no
  mesmo campo; `Calendar` é campo **e** util, então o nome pelado dá o campo e
  `"RUtilsCalendar"` alcança o outro.
- **O `list-presets` precisa do `kind` em alguns nomes.** `brCpf` existe como
  rule _e_ como mask, e sem `kind` vêm os dois.

Um caminho ou um nome que não existe volta como erro listando os válidos, então
um agente que chuta errado se recupera numa chamada a mais.

## O que ele não tem

- **Só inglês.** As ferramentas leem `content/en`; a árvore em português não é
  exposta. Por isso os caminhos vêm **sem** prefixo de idioma — a página de
  `/fields/text` está em `/en/fields/text` no site.
- **Granularidade de página, não de âncora.** Fatiar por título exigiria
  replicar a slugificação de heading do `@nuxt/content`, e um agente quer a
  página inteira de qualquer jeito. Cada resultado leva os `headings` da página,
  então dá para ver o que tem lá dentro antes de ler.
- **Nem resources nem prompts.** Só ferramentas.
- **Nenhuma autenticação**, pelo motivo acima.

## Como ele não desatualiza

É **artefato de build**, não consulta ao vivo. Um módulo Nuxt em `docs/modules/mcp`
lê `content/en`, `app/demos` e `src/runtime/presets` em todo build e escreve um
JSON só, que é o que as ferramentas leem.

É isso que faz a resposta ser idêntica à página: um demo passa pelo mesmo
`demoSourceOf` que o painel de código do site usa, então o fonte que o agente
recebe é byte a byte o que você vê aqui, e o `get-component-api` serve o mesmo
arquivo gerado que as tabelas de props renderizam. É também por isso que o
endpoint é barato — nada consulta o banco de conteúdo em runtime.
