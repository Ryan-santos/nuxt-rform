Esta página é o mapa por dentro. Você não precisa dela para usar o módulo — mas
ela explica por que as coisas se comportam como se comportam, e é o que torna um
campo seu indistinguível de um embutido.

## Um campo é um componente que chama `useField`

Todo campo — embutido ou seu — tem o mesmo formato:

```vue
<script lang="ts">
    import { useField } from "#rform/composables";
    import type { Element } from "#rform/types";
    import type Utils from "#rform/types/components/utils/props";
    import { defineDefaults } from "#rform/utils";

    export const defaults = defineDefaults({
        ui: { container: "flex grow flex-col gap-1" },
        default: ""
    });

    export type Props = Element<typeof defaults, "text"> & Utils["Label"];
</script>

<script setup lang="ts">
    const { id, model, props, tr, locale } = useField(defineProps<Props>());
</script>
```

Dois blocos de script, e a divisão é o contrato:

- **`<script>`** exporta `defaults` e o tipo `Props`. O `defaults` é lido de
  fora — pelo registry gerado, pela árvore de camadas desta documentação, pelo
  `Element` que tipa as props.
- **`<script setup>`** só chama a composable.

## O que `useField` faz

### 1. Acha o pai

Lê o `RForm` (ou `RArray`/`RObject`) por `inject`. Quando há pai **e**
`props.name` está definido, `model.value` lê e escreve **direto** em
`upper.model.value[name]`. É por isso que uma mutação em array no model do filho
reflete no Form: não há cópia no meio.

Sem pai, o campo funciona igual — só não entra em model nenhum.

### 2. Mescla os defaults

Quatro fontes, nesta ordem, no `merger` — e quem chega depois manda:

```
defaults do componente  →  app/rform/defaults.ts  →  props locais  →  props do call site
```

Por isso prop no campo sempre ganha do arquivo de defaults, que sempre ganha do
componente.

### 3. Semeia o `default`

E **clona** ao semear. `props.value.default` é o próprio objeto que o componente
declarou em escopo de módulo — o `merger` copia objeto e array por referência
quando a chave existe numa fonte só. Entregá-lo cru deixava um filho escrever
direto nele, poluindo o default de toda instância seguinte no processo.

### 4. Resolve `rule` e `mask`

As **masks** vêm de `#rform/masks`, importado estaticamente: uma mask é um objeto
literal, e por isso a máscara já está resolvida no primeiro render.

As **rules** vêm de `#rform/presets`, importado **dinamicamente**, e só quando o
campo declara uma `rule`. Toda rule importa zod — um import estático aqui poria zod
no caminho crítico de qualquer página com campo, validado ou não. A rule é
registrada no `RForm` de imediato; quem espera o chunk é a validação, ao rodar.

A `rule` do campo **devolve** a mensagem; quem a escreve no campo é o `RForm`,
que junta o retorno de cada rule com os issues do `:rules` agregado e com o que
vier de fora num mapa só. É por isso que um erro pode aparecer num campo que
ninguém tocou.

## Os utils são componentes de verdade

`RUtilsLabel`, `RUtilsError`, `RUtilsPlaceholder`, `RUtilsLength`,
`RUtilsLoading`, `RUtilsDropdown`, `RUtilsCalendar` e `RUtilsDescription` são
arquivos `.vue` que o campo monta. Eles chamam `useUtil`, que lê as props do
campo pai por injeção — daí a prop `error` viver no campo e a mensagem ser
desenhada pelo util.

A consequência prática: um util **seu** em `app/rform/utils` contribui props a
todo campo que o inclua. É o mecanismo, não uma exceção.

Um deles sai do lugar: o painel do `RUtilsDropdown` — o que `RSelect`, `RDate` e
`RColor` abrem — é teleportado para o `#teleports` do Nuxt, fora do campo. É o
que impede um `transform` ou um `overflow: hidden` num ancestral de deslocar ou
cortar o dropdown. A aparência dele continua sendo o `ui.Utils.Dropdown.popover`
do campo, e ele continua lendo os tokens `--rf-*`, que moram no `:root`.

::callout{type="tip"}
`useField` e `useUtil` são **síncronas**, e é esse o ponto: um campo renderiza
seis utils, e um `setup` assíncrono vira uma boundary de Suspense e um salto de
microtask antes de a subárvore existir — pagos até pelos cinco utils que decidem
não renderizar nada. É o build entregar o `defaults` na própria chamada que
torna isso possível.
::

## O registry é gerado

O `module.ts` escaneia `src/runtime/components/{fields,utils}` e
`app/rform/{fields,utils}`, na ordem embutido→usuário — quem vem depois vence.
Desse escaneamento único saem os tipos, o `components-map`, o `FieldType`, as
raízes que o vite plugin reescreve e o `#rform/registry` — que hoje guarda só os
nomes que o build conhece, para a composable recusar um componente de fora.

O `defaults` não é carregado em runtime: ele chega na chamada, escrito pelo
plugin a partir do `export const defaults` do próprio arquivo.

## A precedência é sempre a mesma

Uma regra só, em cinco lugares:

| o que      | fonte mais fraca               | fonte mais forte       |
| ---------- | ------------------------------ | ---------------------- |
| componente | `src/runtime/components`       | `app/rform/fields`     |
| util       | `src/runtime/components/utils` | `app/rform/utils`      |
| preset     | `src/runtime/presets`          | `app/rform/presets`    |
| `ui`       | `defaults` do componente       | prop `ui` no call site |
| texto      | `defaults.text` prefixado      | o que você passa, cru  |

A exceção é o **pack de tradução**: mesmo code **mescla**, não substitui — é o
que permite a um pack seu de três chaves continuar completo.

## O tema não usa token do Tailwind

Nenhum `ui` do módulo usa token semântico. Toda cor e todo radius passam por uma
variável própria, em forma de arbitrary property:

```ts
container: "rounded-(--rf-radius-xl) bg-(--rf-color-background-100)";
```

São 16 variáveis, e trocar tema é trocar variável. Detalhes em
[Tema](/pt/concepts/tema).

## As libs que fazem o trabalho

O módulo não reimplementa máscara, validação nem posicionamento — ele costura
quatro bibliotecas e expõe uma prop para cada uma. Quando a dúvida é sobre o
comportamento delas, a resposta está na doc delas:

| lib                                                  | o que ela faz aqui                                                     | prop            |
| ---------------------------------------------------- | ---------------------------------------------------------------------- | --------------- |
| [maska](https://beholdr.github.io/maska/)            | aplica a máscara e define os tokens (`#`, `@`, `*`)                    | `mask`          |
| [zod](https://zod.dev)                               | é o que as rules embutidas _são_ — e `rule` aceita um `ZodType` direto | `rule`          |
| [@floating-ui/vue](https://floating-ui.com/docs/vue) | posiciona o painel do `RUtilsDropdown` — `flip`, `shift`, `size`       | —               |
| [vue-i18n](https://vue-i18n.intlify.dev)             | a sintaxe das mensagens, interpolação e plural                         | `text`, `label` |

A lista completa, com o papel de cada uma, está em
[Compatibilidade](/pt/support/compatibilidade#dependencias).
