## O problema

Um formulário tem quatro responsabilidades, e a tentação é dar um lugar a cada
uma: um componente para a UI, um `ref` para o model, uma `interface` para os
tipos e um schema para a validação. Funciona — até o quinto campo, quando
acrescentar um telefone vira quatro edições em quatro arquivos e a que você
esquecer só aparece em produção.

## A decisão

O rform junta as quatro **no campo**:

```vue
<RText
    name="cpf"
    label="CPF"
    mask="brCpf"
    rule="brCpf"
    required
/>
```

- `name` é a chave do model. Não há binding a escrever: o campo lê e escreve
  direto no model do `RForm` pai, por injeção.
- `mask` é o formato. Resolve por nome de preset e, na falta, cai num pattern
  cru do maska.
- `rule` é a validação. Aceita nome de preset, objeto com args, função, zod, ou
  um array de qualquer combinação.
- `required` é a marca visual. Não valida sozinho — de propósito.

## O que sobra para você decidir

Duas coisas, e as duas de fora para dentro:

1. **De onde vêm os tipos e a validação** — é o que os
   [três modos do `useRForm`](/pt/form/form) escolhem.
2. **Como o formulário se parece** — é o que
   [`ui` e `defineFieldDefaults`](/pt/concepts/ui-e-defaults) decidem, sem que
   nenhum campo precise saber.

## Composição, não configuração

Cada campo é montado de peças menores — `RUtilsLabel`, `RUtilsPlaceholder`,
`RUtilsError`, `RUtilsLength`, `RUtilsLoading` — que leem as props do campo pai
pelo `useUtil`. Isso não é detalhe interno: é a razão de um util **seu**, em
`app/rform/utils`, passar a contribuir props a todo campo que o inclua.

O mesmo vale para os campos: um `.vue` em `app/rform/fields` é um campo de
primeira classe — entra no `FieldType`, no `components-map` e no
`defineFieldDefaults`, e pode ser alvo do `available` de um preset. Veja
[Campos próprios](/pt/concepts/campos-proprios).
