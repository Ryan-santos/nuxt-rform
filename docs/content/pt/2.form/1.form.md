`RForm` não é um campo: é quem provê a raiz da injeção. Todo campo dentro dele
lê o model do formulário por `inject`, e é isso que faz `name` significar "esta
chave do model" em vez de "este input isolado".

Ele também é quem provê o **form root** — o `form` que toda `rule` recebe. Nem
`RArray` nem `RObject` o sobrescrevem, então um campo aninhado a três níveis
continua enxergando o formulário inteiro.

## Os três modos do useRForm

O que muda entre eles é **de onde vêm** a UI, os tipos e a validação.

### 1 · schema completo

`useRForm(schema)` devolve `data`, `rules` e `schema`. O `RForm` recebe o schema
e monta o formulário sozinho — não há uma única tag de campo escrita à mão.

::demo{src="Form/modo-schema" title="o schema é o dado" :form="false"}
::

::callout{type="info"}
Em modo `schema` cada campo já carrega o próprio `rule`, então passar `:rules`
aqui validaria duas vezes — o mesmo preset, a mesma mensagem, um parse a mais. O
`:rules` existe para o **modo zod**, onde a UI é escrita à mão e o agregado é a
única fonte.
::

### 2 · só zod

Passando um objeto só de `ZodType`, o `useRForm` devolve `data` e `rules` — e
nada de `schema`. A UI é sua; o `rules` agregado valida o objeto inteiro no
submit, e é o `:rules` do `RForm` que o consome: cada issue do zod pousa no campo
que a possui, pelo caminho do `path`.

::demo{src="Form/modo-zod" title="tipos e validação do zod, UI à mão" :form="false"}
::

### 3 · só TS

`useRForm<T>()` não recebe nada em runtime: só tipa o `data`. Sem `rules` e sem
`schema` — quem valida são os presets declarados em cada campo.

::demo{src="Form/modo-ts" title="zero custo em runtime" :form="false"}
::

::callout{type="warn"}
`safeParseAsync`, e não `safeParse`: uma `rule` referenciada por nome de preset
vira `z.any().superRefine(async …)` no objeto agregado, e um parse síncrono
lançaria. Um schema só-zod continua síncrono.
::

## Erros vindos de fora

Nem todo erro nasce no navegador. "CPF já cadastrado" só existe depois que o
servidor respondeu, e para esse caso o `RForm` tem duas portas — as duas
chaveadas pelo `name` do campo.

A primeira é o **retorno do `onSubmit`**: devolver um objeto de erros faz cada
mensagem pousar no campo que a possui.

```ts
const enviar = async (data: Cadastro) => {
    const { errors } = await $fetch("/api/cadastro", { method: "POST", body: data });

    // Nada devolvido = deu certo. Um objeto = erro por campo.
    return errors;
};
```

A segunda é `setErrors`, pelo `ref` do template — para um erro que não veio de um
submit.

```vue
<template>
    <RForm ref="form" v-model="data">
        <RText name="nome" />
    </RForm>
</template>

<script setup lang="ts">
    const form = useTemplateRef("form");

    form.value?.setErrors({ nome: "Nome já registrado" });
</script>
```

::demo{src="Form/erros-api" title="o servidor escreve no campo" :form="false"}
::

A chave é o `name` do campo, e ela pode chegar **aninhada** ou **pontilhada** —
as duas dão no mesmo, inclusive misturadas. O índice de um `RArray` entra como um
segmento qualquer:

```ts
{ endereco: { cep: "CEP inválido" } }   // aninhada
{ "endereco.cep": "CEP inválido" }      // pontilhada
{ "socios.0.cpf": "CPF inválido" }      // dentro de um RArray
{ nome: ["Já existe"] }                 // string[] → o primeiro item
```

A mensagem que entra por aqui é **texto final**, não chave: ela veio do servidor,
que já sabe em que idioma responder, e o módulo a escreve no campo sem passar pelo
tradutor. Quem aceita chave é o `:error` de um campo — ver
[Tradução](/pt/concepts/traducao).

::callout
Este é o **único** canal em modo `schema` e no [`RDynamic`](/pt/form/dynamic):
lá não há tag de campo escrita à mão para receber um `:error`.
::

Um issue de raiz — um `superRefine` no objeto inteiro, sem `path` — vira a chave
`""`. Nenhum campo tem esse `name`, então ele aparece no retorno do `submit` e não
renderiza em lugar nenhum.

O `ref` do template expõe `model`, `validate`, `submit`, `setErrors` e `errors`;
o slot default expõe os quatro últimos menos `errors`. `validate()` devolve
`true`/`false` e nunca rejeita; `submit()` devolve `undefined` quando tudo passou,
ou o mapa de erros.

## Foco no primeiro erro

Sempre que um erro aparece — na validação ou num `setErrors` vindo da API — o
primeiro campo com erro recebe foco e a tela rola até ele. "Primeiro" é em ordem
de **documento**, não de registro: quem responde é o DOM, então vale igual para o
formulário escrito à mão e para o que o `RDynamic` montou.

Para desligar:

```vue
<RForm :focus-error="false" v-model="data">
```
