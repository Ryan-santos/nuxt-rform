Um formulário raramente é uma lista plana. O CEP só interessa quando a entrega é
em casa; o corpo da requisição só existe quando o tipo não é `none`.

No modo template isso já está resolvido: você escreve o `v-if` do próprio Vue. No
modo `schema` **não há markup onde escrevê-lo** — um `<RDynamic :schema>` vindo de
uma rota do servidor precisa dizer isso no dado. É o que `visibleWhen` e
`disabledWhen` resolvem, e é por isso que as duas são chaves do **schema**, não
props de campo.

::

## Onde elas valem

Quem lê as duas é o `RDynamic`: é ele que decide se monta o campo e é ele que
preenche o `disabled` dele.

::callout{type="warn"}
**Numa tag escrita à mão elas não existem.** `<RText :visible-when="…">` não casa
com prop nenhuma e cai como atributo solto. Em markup a resposta é o `v-if`:

```vue
<RTextarea
    v-if="data.tipo !== 'none'"
    name="body"
/>
```
::

Um campo que sai da tela por `v-if` também sai da validação — ele desmonta e leva a
própria `rule` junto.

## A forma da condição

```ts
{ field: "entrega", op: "===", value: "casa" }
```

`field` é um caminho **pontilhado a partir da raiz do formulário**, sempre — nunca
relativo ao campo que declara a condição. Vale descer em objeto e em índice de
array:

```ts
{ field: "endereco.uf", op: "===", value: "SP" }
{ field: "socios.0.cpf", op: "is_not_empty" }
```

::callout{type="warn"}
**`op` é obrigatório e não tem default.** `{ field: "idade", value: 18 }` não
compila. A diferença entre `==` e `===` fica escrita no schema, que é onde ela
precisa estar quando você não controla se o campo devolve `"18"` ou `18`.
::

## Os operadores

| `op`                      | o campo             | `value`         | casa quando                                  |
| ------------------------- | ------------------- | --------------- | -------------------------------------------- |
| `==` `!=` `===` `!==`     | qualquer            | qualquer        | o operador homônimo do JS                    |
| `>` `>=` `<` `<=`         | número, texto, data | idem            | a comparação do JS                           |
| `in` `not_in`             | escalar             | **array**       | o campo está na lista                        |
| `contains` `not_contains` | texto ou lista      | escalar         | o campo contém o valor                       |
| `starts_with` `ends_with` | texto               | texto           | começa / termina com                         |
| `matches`                 | texto               | padrão de regex | `new RegExp(value, flags).test(campo)`       |
| `is_empty` `is_not_empty` | qualquer            | —               | vazio: `undefined`, `null`, `""`, `[]`, `{}` |

`in` e `contains` são inversos, e os dois existem: o primeiro pergunta se o campo
está numa lista fixa do schema, o segundo se o campo — um `RSelect multiple`, um
texto — contém um item.

`is_empty` **não casa** `false` nem `0`: o campo respondeu.

Só o `matches` aceita `flags`, e ele precisa, porque `(?i)` não existe em
JavaScript:

```ts
{ field: "cupom", op: "matches", value: "^promo", flags: "i" }
```

## Compondo

Um array é **E**, `{ or }` é **OU**, `{ not }` inverte — e os três aninham.

```ts
// aparece quando é entrega em casa E o CEP já foi preenchido
visibleWhen: [
    { field: "entrega", op: "===", value: "casa" },
    { field: "cep", op: "is_not_empty" }
]

// aparece quando é PJ OU o faturamento passa de mil
visibleWhen: {
    or: [
        { field: "tipo", op: "===", value: "pj" },
        { field: "faturamento", op: ">", value: 1000 }
    ]
}

visibleWhen: { not: { field: "tipo", op: "in", value: ["pf", "mei"] } }
```

Quando o declarativo não alcança, uma função recebe o mesmo par que uma `rule`
recebe — `value` é o valor do próprio campo, `form` é o formulário inteiro:

```ts
visibleWhen: ({ form }) => form.itens.length > 3;
```

::callout{type="info"}
A tipagem cobre **quatro níveis** de aninhamento, que é `[{ or: [{ not: […] }] }]`.
O avaliador em runtime não tem limite; só o autocompletar para aí.
::

## O que acontece com o valor, e com a validação

**Campo escondido sai da validação e mantém o valor no model.** As duas metades
importam:

- sai da validação — um `rule: "required"` num campo que não está na tela não pode
  reprovar o submit, e isso vale para as três fontes de erro (a `rule` do campo, o
  `:rules` agregado e um upload pendente);
- mantém o valor — voltar a mostrar o campo devolve o que já estava digitado, e o
  que você enviar ao servidor continua sendo o model inteiro. Se um campo escondido
  não deve ir junto, apague a chave no `onSubmit`.

Esconder um `object` derruba também os erros dos filhos dele.

::callout{type="warn"}
**`disabled` continua sendo validado.** Ele mexe em interação e aparência; o valor
está no model do mesmo jeito, e o HTML não é a autoridade sobre isso. Quem quer
tirar da validação usa `visibleWhen`.
::

## `disabled` e `disabledWhen`

`disabled` é prop de todo campo, e vale nos dois modos:

```vue
<RText name="entrega" disabled />
```

`disabledWhen` é a versão do schema, e a prop explícita **vence** a condição, nos
dois sentidos — `disabled: false` mantém o campo ligado mesmo que a condição diga o
contrário:

```ts
{
    entrega: { type: "text", label: "Endereço" },
    complemento: {
        type: "text",
        disabledWhen: { field: "entrega", op: "is_empty" }
    }
}
```

O campo desabilitado ganha `pointer-events-none opacity-60` no container e o
`disabled` nativo no controle, que é o que o tira do Tab. Para restilizar, a chave
é `ui.disabled`.

::callout
`disabled` num `object` ou num `array` **não cascateia** para os filhos: o CSS
bloqueia o mouse, mas não tira ninguém do Tab. Quem quer filho desabilitado põe
`disabledWhen` no filho.
::

## snake_case no schema

No schema o objeto costuma vir de uma API, e ali `visible_when` é aceito tanto
quanto `visibleWhen`. A regra é geral e vale para toda prop composta —
`disabled_when`, `model_full`, `on_search`:

```ts
{
    type: "textarea",
    rule: "required",
    visible_when: { field: "body_type", op: "in", value: ["json", "form"] }
}
```

A tradução é ancorada nas props que o componente de fato declara, então uma chave
que ele não conhece passa intacta e nada é renomeado por engano. Escrevendo as
duas no mesmo campo, a camelCase vence.

## Schema sem `RForm` em volta

A condição é resolvida contra o model do formulário, então um `<RDynamic :schema>`
usado fora de um `RForm` não tem contra o que resolvê-la. Nesse caso ela é
**ignorada** — o campo aparece e fica habilitado — e um aviso vai ao console
nomeando a prop. Esconder o campo calado seria pior.
