Nenhum `ui` do módulo usa token semântico do Tailwind. Toda cor e todo radius
passam por uma variável própria, em forma de _arbitrary property_:

```ts
container: "rounded-(--rf-radius-xl) bg-(--rf-color-background-100) has-[:focus]:outline-(--rf-color-primary)";
```

**Trocar tema é trocar variável — `ui` não se mexe.**

::callout{type="tip"}
As at-rules em volta disso — `@theme`, `@layer`, `@source` e a _arbitrary
property_ `bg-(--var)` — são do **Tailwind 4**, não do rform. A referência é a
[doc de tema do Tailwind](https://tailwindcss.com/docs/theme) e a de
[detecção de fontes](https://tailwindcss.com/docs/detecting-classes-in-source-files).
::

## As 17 variáveis

| grupo  | variáveis                                                                            |
| ------ | ------------------------------------------------------------------------------------ |
| fundo  | `--rf-color-background`, `-100`, `-200`, `-300`                                      |
| texto  | `--rf-color-contrast`                                                                |
| borda  | `--rf-color-border`                                                                  |
| ação   | `--rf-color-primary`, `--rf-color-primary-fg`                                        |
| estado | `--rf-color-danger`, `--rf-color-danger-fg`, `--rf-color-success`, `--rf-color-warn` |
| raio   | `--rf-radius-sm`, `-md`, `-lg`, `-xl`, `-2xl`                                        |

## Elas encadeiam no tema do seu app

O default de cada uma é um `var()` com fallback:

```css
--rf-color-primary: var(--color-primary, #005bdf);
```

Então um app que já tem `primary` no `@theme` **adota sozinho** — não há linha
de override a escrever. Foi assim que este site não precisou de nenhuma.

Os degraus `-100`/`-200`/`-300` (10%, 15%, 20%) são derivados com `color-mix`
em vez de encadeados: um `--color-background-100` de outro app pode significar
"tom mais claro" em vez de "10% na direção do contraste".

`--rf-color-border` encadeia em `--color-border`, e o fallback é translúcido —
`contrast` a 10% sobre `transparent` — em vez de um degrau opaco: a mesma borda
pousa sobre `background` (o grupo do `RArray`) e sobre `-100` (o popover do
`RSelect`, a dropzone do `RFile`), e um tom igual ao `-100` sumiria contra a
própria superfície. É a borda de **repouso**; as de estado (`hover`, arquivo
enviado, arrastando) continuam sendo `primary` e `success`.

## Como sobrescrever

Cinco formas, e a ordem dos dois `@import` só afeta duas delas:

| forma do override no app                        | `#rform` antes | `#rform` depois |
| ----------------------------------------------- | -------------- | --------------- |
| `@theme { --rf-color-primary }`                 | pega           | **ignora**      |
| `@layer base { :root { --rf-color-primary } }`  | pega           | **ignora**      |
| `@layer rform { :root { --rf-color-primary } }` | pega           | pega            |
| `:root { --rf-color-primary }` (fora de layer)  | pega           | pega            |
| `@theme { --color-primary }` (encadeia)         | pega           | pega            |

As três de baixo são imunes à ordem, cada uma por um motivo diferente: mesma
layer resolve por ordem de declaração (e o app vem depois); declaração fora de
layer ganha de toda layer de autor; e `--color-primary` o módulo **nunca**
declara, então não há conflito a resolver — é só o `var(--color-primary, …)` do
default encontrando um valor.

::callout{type="tip"}
As duas formas naturais — encadear pelo `@theme` do seu app, ou declarar
`--rf-*` dentro de `@layer rform` — funcionam nas **duas** ordens. Quem quebra é
declarar `--rf-*` **fora** da `@layer rform` com o `#rform` importado depois — e
aí quebra calado.
::

### Exemplo, encadeando

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@theme {
    --color-primary: oklch(0.6 0.2 250);
}
```

### Exemplo, direto

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@layer rform {
    :root {
        --rf-color-primary: oklch(0.6 0.2 250);
        --rf-radius-xl: 0.25rem;
    }
}
```

## O que fica literal, de propósito

- `*-current/*` — já é `currentColor`.
- `bg-transparent`, `outline-transparent`.
- `rounded-{full,none,l-none,r-none}` — estruturais, não de tema.
- O `bg-[linear-gradient(…#f00…)]` do matiz no `RColor`.
- O `border-white` dos marcadores do color picker — branco **por desenho**, para
  contrastar com uma cor arbitrária.

Note a assimetria: `text-white` seria drift (virou `-fg`), `border-white` não é.

## Os ícones

Cor e radius são variável; ícone é **alias**. O rform declara `@nuxt/icon` como
dependência de módulo e registra os 16 que usa sob o namespace `rform:`:

| grupo     | aliases                                                                     |
| --------- | --------------------------------------------------------------------------- |
| ação      | `rform:plus`, `rform:minus`, `rform:remove`, `rform:check`                  |
| navegação | `rform:select`, `rform:search`, `rform:chevron-left`, `rform:chevron-right` |
| estado    | `rform:loading`, `rform:alert`                                              |
| arquivo   | `rform:file`, `rform:image`, `rform:upload`, `rform:retry`, `rform:cancel`  |
| data      | `rform:calendar`                                                            |

**Trocar um ícone é sobrescrever o alias**, no `nuxt.config` — não há prop de campo
a procurar:

```ts
export default defineNuxtConfig({
    modules: ["nuxt-rform"],
    icon: {
        aliases: {
            "rform:calendar": "lucide:calendar",
            "rform:remove": "lucide:trash-2"
        }
    }
});
```

::callout{type="tip"}
Sobrescrever um alias **não derruba os outros 15**: o merge do Nuxt é fundo, chave
a chave, e o seu valor ganha só na chave que você escreveu. Escreva um, os quinze
continuam de pé.
::

O namespace é o que mantém os dois lados separados. Os aliases já foram os nomes
curtos (`plus`, `calendar`…), e ali instalar o rform passava a definir 16 aliases
**no seu app** — um `<Icon name="plus" />` numa página sua resolvia para o ícone que
o módulo escolheu, e um alias `calendar` seu **trocava** o ícone do `RDate` sem
ninguém pedir.

### Por instância, quando é o que você quer

O alias vale para o app inteiro. Dois campos abrem uma segunda porta, que vale
naquela tag só — e nela o nome é o do iconify, cru:

```vue
<template>
    <RSwitch
        name="ativo"
        :icon="{ true: 'twemoji:check-mark-button', false: 'twemoji:cross-mark' }"
    />
</template>
```

O outro é o `ui.icon.name` do `RUtilsError`, que é
[`ui`](/pt/concepts/ui-e-defaults) como qualquer outro.

### Nos seus próprios campos

Num `.vue` de `app/rform/fields` ou `app/rform/utils` você escreve o nome do iconify
direto, como em qualquer componente Vue. Mas se o ícone é um dos 16, chame o `icon`
de `#rform/utils`: além de não repetir o nome, ele **acompanha o override** que o app
tenha feito.

```vue
<template>
    <Icon :name="icon('alert')" />
    <Icon name="fa6-solid:star" />
</template>

<script lang="ts">
    import { icon } from "#rform/utils";
</script>
```

::callout{type="warn"}
Nome que não é um dos 16 e não tem `:` renderiza **nada** — só um
`[Icon] failed to load icon` no console. É o modo de falha a conhecer: um
`icon("plux")` com typo não quebra o build nem a lint, ele apaga o ícone.
::

## A guarda

`test/unit/theme.test.ts` cobre cinco casos, e existe por causa de um modo de
falha que só um teste enxerga: `bg-(--rf-color-primry)` — com o typo — compila,
passa na lint e renderiza `var(--undefined)`, ou seja transparente, **calado em
todo ambiente**.

Os cinco: (a) nenhum token semântico cru voltou; (b) o conjunto de `--rf-*` usado
nos componentes é **igual** ao declarado, nos dois sentidos; (c) o template tem
exatamente um `@source` absoluto apontando para um diretório que de fato contém
os componentes; (d) todo token mora dentro de `@layer rform`; (e) o `style.css`
não tem at-rule do Tailwind.

Os ícones têm a própria, `test/unit/icons.test.ts`, pelo mesmo motivo: (a) o
conjunto de nomes que os componentes pedem é **igual** ao dos aliases declarados,
nos dois sentidos; (b) nenhum nome estático sem `:` sobrou num template — que é
exatamente o que apagou quatro ícones quando o namespace entrou; (c) o prefixo do
`icon()` e o nome curto do módulo são a mesma string.
