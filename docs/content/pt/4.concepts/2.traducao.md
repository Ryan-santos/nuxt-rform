O rform não tem nenhum texto cravado em componente. Toda mensagem — o botão do
`RArray`, o placeholder do `RFile`, o erro de uma rule — sai de um _message pack_, e
todo texto que **você** passa numa prop (`label`, `placeholder`, `error`, `description`…)
pode ser uma chave de tradução do seu app.

Há **dois motores**, e o módulo escolhe sozinho em tempo de build:

| seu app            | motor       | o que acontece                                                                              |
| ------------------ | ----------- | ------------------------------------------------------------------------------------------- |
| tem `@nuxtjs/i18n` | **ponte**   | o rform registra os packs dele no store do vue-i18n sob `rform`, e usa o `$i18n` do seu app |
| não tem            | **próprio** | o rform resolve por conta própria, com `@intlify/core`                                      |

Não há configuração para isso. A detecção é `hasNuxtModule("@nuxtjs/i18n")`, e o corpo
do motor da ponte **não escreve** o import do `@intlify/core` — então um app com i18n
não paga os ~137 kB dele. O corte é estrutural, não uma otimização de bundler.

::callout{type="tip"}
A sintaxe das mensagens é a do **vue-i18n** nos dois motores — interpolação
`{param}` e plural `a | b`. A referência é a
[doc de sintaxe do vue-i18n](https://vue-i18n.intlify.dev/guide/essentials/syntax.html);
a do módulo do Nuxt, com `langDir`, `strategy` e o resto da configuração que o
rform lê, é a do [@nuxtjs/i18n](https://i18n.nuxtjs.org).
::

## `tr`, a única função

Todo campo e todo util recebe `tr` das composables, sem escrever import:

```vue
<script setup lang="ts">
    const { props, tr } = useUtil<Props>();
</script>
```

Ela aceita quatro formas:

```ts
tr("form.nome"); // chave do seu app
tr({ key: "form.max", params: { n: 30 } }); // chave do seu app, com parâmetros
tr("rform.formats.date"); // chave do módulo, caminho por extenso
tr("~~Nome"); // literal explícito
```

`tr` lê o locale a cada chamada, então uma chamada dentro de template rastreia o ref e
**trocar de idioma re-renderiza** — inclusive reformatando datas, porque o formato de
exibição também vem do pack.

### O algoritmo

```
COM PONTE                          SEM PONTE
1. "~~…"  → remove o marcador      1. "rform.…" → resolve no pack do módulo
2. resto  → $i18n.t(chave)         2. resto     → devolve a string como está
```

::callout{type="warn"}
**A assimetria é deliberada.** Sem `@nuxtjs/i18n` não existe nada contra o que
resolver uma chave do app, então `tr` é a identidade — e `~~Nome` imprime
literalmente `~~Nome`. Um componente escrito pensando num app com i18n tem esse
custo num app sem. É aceito, não é bug.
::

::demo{src="Traducao/chave-vs-literal" title="chave do app, ou literal com ~~"}
Troque o idioma no rodapé da barra lateral: o primeiro campo muda, o segundo não.
::

::demo{src="Traducao/parametros" title="chave com parâmetros"}
Quando a mensagem interpola, a prop recebe a forma de objeto — e o tipo dos params
vem do próprio texto da mensagem.
::

::demo{src="Traducao/mensagens-do-modulo" title="as mensagens do próprio módulo"}
O botão do `RArray` e o texto de busca do `RSelect` saem do pack do módulo,
registrado sob `rform`. Nada aqui declara esses textos.

## `TrInput`: o tipo é gerado do **seu** arquivo de mensagens

Toda prop de texto é tipada como `TrInput`, e `TrInput` é **gerado** a partir do
arquivo de locale que o seu app declara no `@nuxtjs/i18n`.

```ts
// nuxt.config.ts
i18n: {
    defaultLocale: "pt-BR",
    langDir: "locales",
    locales: [
        { code: "pt-BR", name: "Português", file: "pt-BR.json" },
        { code: "en", name: "English", file: "en.json" }
    ]
}
```

```json
// i18n/locales/pt-BR.json
{
    "form": {
        "nome": "Nome",
        "max": "No máximo {n} caracteres",
        "itens": "um item | {n} itens"
    }
}
```

Daí sai:

```ts
<RText label="form.nome" />                             // ✅
<RText :description="{ key: 'form.max', params: { n: 30 } }" />  // ✅
<RText label="Nome" />                                  // ❌ erro de compilação
<RText label="~~Nome" />                                // ✅ literal explícito
```

O gerador lê o arquivo do `defaultLocale`, achata em caminhos pontilhados e infere os
parâmetros do próprio texto da mensagem: `{n}` vira `{ n: Interp }`, um `|` vira uma
escolha de plural (`number`), e os dois juntos viram a união.

### Os quatro modos

| situação                                         | `TrInput`                                         | por quê                                             |
| ------------------------------------------------ | ------------------------------------------------- | --------------------------------------------------- |
| `.json` legível                                  | `Paramless \| ModuleKey \| WithParams \| Literal` | rigor completo                                      |
| i18n sem `file` declarado                        | `ModuleKey \| Literal`                            | não há chave do app para oferecer, mas o rigor fica |
| `file` em `.ts`, yaml, ou loader de `lazy: true` | `string`                                          | + um aviso de build nomeando o arquivo              |
| sem `@nuxtjs/i18n`                               | `string`                                          | não há app i18n a respeitar                         |

Só `.json` é lido — é `JSON.parse`, zero dependência. As duas degradações são
diferentes de propósito: **sem arquivo** ainda exige chave-ou-`~~`; **arquivo
ilegível** solta para `string`, porque ser rigoroso ali rejeitaria toda chave válida.

## Sobrescrever uma mensagem do módulo

### Com `@nuxtjs/i18n`

Declare a chave sob `rform` no locale do **seu** app. É a precedência normal do
vue-i18n, sem nada específico do módulo:

```json
{
    "rform": {
        "fields": { "array": { "add": "Incluir" } },
        "presets": { "rules": { "required": "Preencha este campo." } }
    }
}
```

### Sem `@nuxtjs/i18n`

Crie `app/rform/locales/<code>.ts`. **Mesmo code mescla**, não substitui — diferente de
campo, util e preset, onde mesmo nome troca o arquivo inteiro. Um pack de três chaves
continua completo:

```ts
import { defineLocale } from "#rform/utils";

export default defineLocale({
    fields: {
        array: { add: "Incluir" }
    }
});
```

Um code novo (`es`) simplesmente entra; o que faltar cai no pack default. O idioma
inicial vem da opção do módulo:

```ts
// nuxt.config.ts
rform: {
    locale: "pt-BR";
} // default
```

Sem ponte, o locale ativo é um `useState("rform-locale")` — escreva nele para trocar de
idioma.

::demo{src="Traducao/text-prop" title="trocando uma mensagem numa instância"}
A prop `text` espelha o `defaults.text` do componente, aninhada — e o que você
passa entra cru, sem prefixo.
::

## O mapa de chaves do módulo

```
rform.
  fields.array.add
  fields.select.search
  fields.file.{placeholder,loading,zero,bytes.{b,kb,mb,gb,tb}}
  fields.date.{hint,hintTime,separator}
  fields.hour.{hint,separator}
  utils.calendar.{start,end,time}
  presets.rules.{required,email,url}
  presets.rules.min.{number,length}
  presets.rules.max.{number,length}
  presets.rules.br.{cpf,cnpj,cep,telefone}
  formats.date
```

`fields.*` e `utils.*` espelham `components/fields` e `components/utils`. É de lá que o
prefixo automático sai — e é o que permite um campo e um util de mesmo nome (`Calendar`
é os dois) conviverem.

`formats.date` não é texto: é o padrão (`DD/MM/YYYY`) do qual saem a máscara, o regex de
parse e a formatação de exibição. Traduzi-lo é como o `RDate` muda de formato por idioma.

## Escrevendo um campo ou util traduzível

Declare as chaves em `defaults.text` e derive as props com `TextProp`:

```vue
<template>
    <button>{{ tr(props.text?.button) }}</button>
</template>

<script lang="ts">
    export const defaults = defineDefaults({
        ui: { container: "flex flex-col gap-1" },
        default: [],
        text: {
            button: "add"
        }
    });

    export type Props = Element<typeof defaults, "array"> &
        Utils["Label"] &
        TextProp<typeof defaults.text>;
</script>
```

Três coisas acontecem sozinhas:

1. **O valor é prefixado** com `rform.fields.<componente>.` (ou `rform.utils.<nome>.`
   num util), então `"add"` vira `rform.fields.array.add`.
2. **`TextProp` gera o tipo da prop** — `{ text?: { button?: TrInput } }`. Você não
   reescreve as chaves.
3. **Quem passa a prop ganha**, cru. O prefixo acontece _antes_ do merge, então a
   procedência sai de graça:

```ts
<RArray :text="{ button: 'form.adicionar' }" />              // → "form.adicionar" (cru)
defineFieldDefaults({ Array: { text: { button: "meu.add" } } }) // → "meu.add"      (cru)
// nada passado                                              // → "rform.fields.array.add"
```

### Grupos aninhados

O grupo entra no caminho, então a árvore espelha o pack:

```ts
text: {
    loading: "loading",
    bytes: { kb: "kb", mb: "mb" }
}
// → rform.fields.file.loading, rform.fields.file.bytes.kb, …
```

E `TextProp` acompanha:

```ts
TextProp<{ hint: string; teste: { a: string } }>;
// → { text?: { hint?: TrInput, teste?: { a?: TrInput } } }
```

### `label` e `placeholder` ficam **fora** de `text`

São props que o app passa direto, por contrato, então moram no topo:

```ts
export const defaults = defineDefaults({
    ui: { … },
    default: null,
    placeholder: "placeholder",   // ← topo, não dentro de text
    text: { loading: "loading" }
});
```

Um valor que o **componente** declarou ali ainda é mensagem do módulo, então também é
prefixado (`rform.fields.file.placeholder`). String vazia é o sentinela de "não
renderiza nada" e passa intacta.

### Nomeando chaves

Não repita "text" dentro de `text`: `text: { buttonText }` é ruído, `text: { button }`
é o certo — o caminho de leitura já diz (`props.text.button`).

## Rules

Uma rule não é componente e não pode chamar composable, então ela **importa** o
tradutor:

```ts
import { defineRule, trRule, type RuleContext } from "#rform/utils";

export default defineRule({
    validation: ({ value, min }: RuleContext<{ min: number }>) =>
        value.length >= min ? undefined : trRule({ key: "min.length", params: { min } })
});
```

`trRule` é só açúcar: prefixa `rform.presets.rules.`. Para uma mensagem do **seu app**,
use `tr` direto — ele aceita o caminho completo.

O contexto da validation é `{ value, form, ...args }` e nada mais.

### Plural

As mensagens de `min`/`max` são plurais de verdade:

```ts
"Mínimo de {min} caractere. | Mínimo de {min} caracteres.";
```

Um **número dentro dos parâmetros nomeados escolhe a forma**, então o call site não
repete o valor: `trRule({ key: "min.length", params: { min: 1 } })` dá "Mínimo de 1
caractere." e `{ min: 5 }` dá "…5 caracteres.".

::demo{src="Traducao/rules" title="mensagem de rule, e plural de verdade"}
Rode o submit: `min 1` diz "caractere" e `min 5` diz "caracteres".
::

## Gotchas

### Um `@` literal precisa de escape

`@:chave` é a sintaxe de _mensagem ligada_ do vue-i18n. Um e-mail cru numa mensagem
derruba o parser:

```
Invalid linked format (error code: 10)
target message: voce@empresa.com
target message path: form.emailExemplo
```

Escreva `{'@'}`:

```json
{ "emailExemplo": "voce{'@'}empresa.com" }
```

::demo{src="Traducao/arroba" title="o placeholder escapado"}
::

O gerador de tipos remove as interpolações literais `{'…'}` **antes** de procurar
parâmetros, então o escape não inventa um parâmetro chamado `@`.

### O locale do app manda na lista de idiomas

A ponte registra os packs do módulo **sob os codes que o seu app declarou**, escolhendo
por code exato e, na falta, por língua. Um app com `locales: ["pt", "es"]` continua com
`["pt", "es"]`: o `pt` recebe o pack `pt-BR`, o `es` não recebe nada e cai no
`fallbackLocale` do vue-i18n.

Isso é deliberado — registrar um code que o app não declarou o faria aparecer no
seletor de idioma dele, no `localeCodes` e no prerender.

### O que **não** é traduzido

O model. `formatIso*` e o ramo ISO de `parseIncoming` são locale-independentes por
definição: localizá-los faria o valor gravado mudar com o idioma da tela. Só a
_exibição_ segue `formats.date`.

### Custo sem i18n

Num app **sem** `@nuxtjs/i18n`, o `@intlify/core` entra no bundle: ~137 kB
(`core-base` 66 kB + `message-compiler` 57 kB + `shared` 14 kB). Num app **com**, zero —
a ponte usa o vue-i18n que já está lá.

`@intlify/core` é `dependencies`, não peer opcional: o caminho sem i18n é o comum, e um
peer opcional faria o caso padrão exigir instalação manual.
